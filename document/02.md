# 02. 数据竞争实验：为什么 `counter++` 会丢

这一节要解决的是一个非常典型的问题：多个线程同时去改同一个变量，到底会发生什么。

实验拆成了两段：先做无锁版本，再做 mutex 修复版本。`atomic` 暂时只作为扩展对比，不放进主线里。

## 1. 本节目标

1. 先把数据竞争（race condition）真正观察出来。
2. 确认一件事：看起来最简单的自增，也可能在并发下出错。
3. 把 `std::mutex` + `std::lock_guard` 的用法练熟。
4. 建立一个判断习惯：只要出现“共享数据 + 并发写”，就必须考虑同步。

## 2. 关键概念

### 2.1 数据竞争（data race）

满足下面这三个条件，我就要高度怀疑数据竞争：

1. 多个线程并发访问同一内存位置。
2. 至少一个线程在写。
3. 没有同步保护。

我后来更明确地意识到：数据竞争不只是“结果偏一点”，它本身就是未定义行为，后果可能非常不可预测。

### 2.2 临界区（critical section）

- 访问共享资源的那段代码就是临界区。
- 临界区需要串行化，也就是同一时刻只能有一个线程进入。

### 2.3 互斥锁（`std::mutex`）

- 用于保护临界区。
- 拿到锁的线程进入临界区，其余线程等待。

### 2.4 `std::lock_guard<std::mutex>`

- RAII 风格封装：构造时加锁，析构时自动解锁。
- 比手写 `lock()` / `unlock()` 更安全，也更不容易因为异常或早退而忘记解锁。

## 3. 为什么 `counter++` 也会出问题

`counter++` 不是一个不可分割的单步动作，逻辑上通常包含：

1. 读取旧值。
2. 计算 +1。
3. 写回新值。

并发下，两个线程很可能读到相同旧值，最后写回时彼此覆盖，结果就是“丢计数”。

## 4. 语法补充：函数传参方式

这一节我最想弄明白的，其实是“线程函数参数到底是怎么传进去的”。

### 4.1 `std::thread` 默认按值传参

创建线程时：

```cpp
std::thread t1(Counter, std::ref(counter));
```

`std::thread` 在构造时会把参数保存起来，并在新线程启动时传给目标函数。默认情况下，它会把参数当作“可拷贝对象”处理，也就是倾向于按值保存。

这意味着：如果我直接写 `std::thread t1(Counter, counter);`，线程函数拿到的可能不是我想要的“同一个共享变量”，而是一个副本。

### 4.2 为什么这里要用 `std::ref`

你的无锁版本和加锁版本里都写了：

```cpp
std::ref(counter)
```

它的作用，是把变量包装成“引用传递”的形式，告诉 `std::thread`：这里不要拷贝，请把原对象本身传给线程函数。

这一步非常关键，因为我这一节要演示的，正是“多个线程操作同一个共享计数器”。如果不传引用，就不会形成真正的共享访问，也就很难复现数据竞争。

### 4.3 函数参数里的引用写法

你的函数原型是：

```cpp
void Counter(int& count)
void MutexCounter(int& count, std::mutex& mtx)
```

这里的 `int&` 和 `std::mutex&` 表示“引用参数”：

1. `int& count` 让我能直接操作外部的 `counter`。
2. `std::mutex& mtx` 让两个线程共享同一把锁，而不是各自拿一个副本。

如果 `mutex` 不是引用，而是按值传递，代码要么无法编译，要么就失去“保护同一共享资源”的意义。

### 4.4 `std::lock_guard` 的作用范围

在加锁版本里：

```cpp
std::lock_guard<std::mutex> lock(mtx);
++count;
```

这表示：

1. `lock_guard` 构造时自动加锁。
2. 当前循环这一轮的临界区只有 `++count`。
3. 离开这次循环作用域时，`lock_guard` 自动析构并解锁。

这种写法比手动 `lock()` / `unlock()` 更安全，因为即使未来代码里加入 `return`、异常或其他分支，也不容易忘记解锁。

### 4.5 这组接口的组合关系

这一段代码其实同时演示了三件事：

1. `std::thread` 如何把函数和参数交给新线程执行。
2. `std::ref` 如何把共享变量按引用送入线程。
3. `std::mutex` + `std::lock_guard` 如何保护共享写入。

这也是为什么我觉得这份代码不只是“跑出来了结果”，它还很适合当作本节的第一个完整实验。

### 4.6 常用接口、常见用法与关系

这一小节我把本节里最常见的接口放在一起，主要看三件事：

1. 每个接口解决什么问题。
2. 常见写法是什么。
3. 它和其它接口如何配合。

#### 4.6.1 接口速览

1. 线程创建与管理
- `std::thread(fn, args...)`：启动新线程执行函数。
- `joinable()`：线程对象当前是否还能 `join` 或 `detach`。
- `join()`：等待线程结束并回收管理关系。
- `detach()`：分离线程，不再由当前线程对象管理。
- `std::this_thread::get_id()`：拿当前线程 ID。

2. 参数传递
- `std::ref(x)`：把 `x` 以引用语义传给线程函数。
- `std::cref(x)`：以只读引用语义传参。

3. 互斥保护
- `std::mutex`：互斥锁本体。
- `lock()` / `unlock()`：手动加解锁（易出错，慎用）。
- `try_lock()`：尝试加锁，不阻塞。
- `std::lock_guard<std::mutex>`：作用域自动加解锁，首选。
- `std::unique_lock<std::mutex>`：更灵活，可延迟加锁/手动解锁（后续条件变量常用）。

#### 4.6.2 他们之间的关系

我现在更愿意把这组接口理解成一条链路：

1. `std::thread` 负责“并发执行”。
2. `std::ref` 负责“把同一份共享对象交给多个线程”。
3. `std::mutex` 负责“限制同一时刻只能一个线程进入临界区”。
4. `std::lock_guard` 负责“把加锁/解锁变成作用域自动管理”。
5. `join()` 负责“在线程结束点做生命周期收尾”。

如果缺少其中任一环，常见后果大概是：

1. 不用 `std::ref`：可能操作的是副本，不是共享数据。
2. 不加 `mutex`：共享写入会出现 race。
3. 不用 RAII 锁：容易忘记解锁。
4. 不 `join`/`detach`：线程对象析构时可能触发终止。

#### 4.6.3 实际代码示例 A：按值传参与按引用传参

```cpp
#include <iostream>
#include <thread>
#include <functional>

void inc(int& x) {
    ++x;
}

int main() {
    int a = 0;
    int b = 0;

    // 按值：线程拿到的是副本，外部 a 不变
    std::thread t1([](int x) { ++x; }, a);

    // 按引用：线程修改的是外部 b 本体
    std::thread t2(inc, std::ref(b));

    t1.join();
    t2.join();

    std::cout << "a=" << a << ", b=" << b << std::endl; // 常见结果: a=0, b=1
    return 0;
}
```

关键点：`std::thread` 默认更接近“值语义传参”，共享对象必须显式 `std::ref`。

#### 4.6.4 实际代码示例 B：手动锁与 RAII 锁对比

```cpp
#include <iostream>
#include <thread>
#include <mutex>

std::mutex m;
int counter = 0;

void bad_manual_lock() {
    m.lock();
    ++counter;
    // 如果这里提前 return 或抛异常，unlock 可能被跳过
    m.unlock();
}

void good_raii_lock() {
    std::lock_guard<std::mutex> lock(m);
    ++counter;
} // 离开作用域自动解锁

int main() {
    std::thread t1(good_raii_lock);
    std::thread t2(good_raii_lock);
    t1.join();
    t2.join();
    std::cout << "counter=" << counter << std::endl;
    return 0;
}
```

关键点：本节里我会优先使用 `std::lock_guard`，它比手动 `lock/unlock` 更稳妥。

#### 4.6.5 实际代码示例 C：`joinable` + `join` 的安全收尾

```cpp
#include <thread>
#include <chrono>

void work() {
    std::this_thread::sleep_for(std::chrono::milliseconds(10));
}

int main() {
    std::thread t(work);

    if (t.joinable()) {
        t.join();
    }

    return 0;
}
```

关键点：`joinable()` 常用于防御式检查，避免重复 `join` 或对无效线程对象操作。

## 5. 实验主线

我在 [src/main.cpp](../src/main.cpp) 里完成了两个阶段的实验。

### 5.1 阶段 A：无锁版本（复现问题）

1. 共享计数器 `counter = 0`。
2. 启动 2 个线程。
3. 每个线程执行 `counter++` 共 `N` 次（建议 `N = 100000` 或更大）。
4. `join` 后输出：
- 期望值：`2 * N`
- 实际值：`counter`

目标：观察结果是否会偏小，或者是否每次都不一样。

### 5.1.1 复现代码
```cpp
#include <iostream>
#include <thread>
const int N = 100000;
int counter = 0;

void Counter(int& count) {
    for (int i = 0; i < N; ++i) {
        ++count;
    }
}

int main() {
    std::thread t1(Counter, std::ref(counter));
    std::thread t2(Counter, std::ref(counter));
    t1.join();
    t2.join();
    std::cout << "Final counter value: " << counter << std::endl;
    return 0;
}
```

我实际跑了三次（`N = 100000`），终端输出大概是这样：
```text
Final counter value: 140664
Final counter value: 143587
Final counter value: 143156
```

最终值都小于 `200000`，所以我确认自己已经成功复现了数据竞争。

### 5.2 阶段 B：mutex 版本（修复问题）

1. 重置计数器为 0。
2. 同样启动 2 个线程，每次自增前用 `std::lock_guard<std::mutex>` 保护。
3. `join` 后输出：
- 期望值：`2 * N`
- 实际值：`counter`

目标：结果稳定等于期望值。

```cpp
#include <iostream>
#include <thread>
#include <mutex>
const int N = 100000;
int counter = 0;

void Counter(int& count) {
    for (int i = 0; i < N; ++i) {
        ++count;
    }
}

void MutexCounter(int& count, std::mutex& mtx) {
    for (int i = 0; i < N; ++i) {
        std::lock_guard<std::mutex> lock(mtx);
        ++count;
    }
}

int main() {
    std::cout << "---- NoLock Counter Example ----" << std::endl;
    std::thread t1(Counter, std::ref(counter));
    std::thread t2(Counter, std::ref(counter));
    t1.join();
    t2.join();
    std::cout << "Final counter value: " << counter << std::endl;

    counter = 0; // reset
    std::cout << "---- Mutex Counter Example ----" << std::endl;
    std::mutex mtx;
    std::thread t3(MutexCounter, std::ref(counter), std::ref(mtx));
    std::thread t4(MutexCounter, std::ref(counter), std::ref(mtx));
    t3.join();
    t4.join();
    std::cout << "Final counter value: " << counter << std::endl;
    return 0;
}
```
