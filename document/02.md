# 数据竞争实验：为什么 `counter++` 会丢

上一篇介绍了线程的生命周期——线程能启动、能正确退出。但光是能启动还不够。多线程编程真正的挑战，从多个线程开始操作同一份数据的那一刻起才算开始。

## 0. 实验：数据竞争

我们来看下面一份代码：
```cpp
#include <iostream>
#include <thread>

const int N = 100000;
int counter = 0;

void count_up(int& c) {
    for (int i = 0; i < N; ++i)
        ++c;
}

int main() {
    std::thread t1(count_up, std::ref(counter));
    std::thread t2(count_up, std::ref(counter));
    t1.join();
    t2.join();
    std::cout << "result: " << counter << "  (expected: " << 2 * N << ")\n";
}
```

按照我们原来的理解，这份代码应该是**两个线程同时对 counter 执行 100000 次自增操作**，所以最终输出应该为
```
result: 200000  (expected: 200000)
```

但是，实际将该代码连跑三次，输出大概是这样：
```
result: 140664  (expected: 200000)
result: 143587  (expected: 200000)
result: 143156  (expected: 200000)
```

可以看到，每次输出都小于期望值，而且都不一样——这个现象叫数据竞争（data race），这种现象也正是数据竞争的特征：结果不对，且不可重复.

## 1. 概念

数据竞争（data race）是指，多个线程同时读写同一块内存，且没加锁保护，导致数据出错。

最典型的场景就是共享计数器：两个线程各自对同一个 `int` 累加 100,000 次，期望结果是 200,000。但实际跑起来，结果往往比 200,000 少很多，而且每次都不一样。代码看上去完全正确，逻辑也没有问题，但就是对不上。

数据竞争是并发编程里最基础也最容易踩的坑，其形成需要满足三个条件：
- 多个线程并发访问同一内存位置
- 至少有一个线程在写
- 没有任何同步保护

数据竞争导致的结果不只是运算结果偏差这么简单。在 C++ 标准中，数据竞争被定义为**未定义行为（UB）**，意思是程序的结果完全不可预测——可能偶尔对，可能每次都错，可能在某个优化级别下跑通但换个编译器就崩，也可能在调试模式下看起来正常但 release 就出问题。

因此，同样需要有一份可能的标准来避免问题，编写更安全高效的代码。

## 2. 发生原理

`counter++` 看起来是一行代码，但在 CPU 层面实际上分三步：
1. 读取（Load）：将 counter 当前的值从内存加载到 CPU 寄存器。
2. 更新（Update）：在寄存器中对这个值执行加 1 运算。
3. 写回（Store）：将寄存器中计算好的新值写回到内存中的 counter 位置。

两个线程并发执行时，这三步可能交错成这样：
```
线程 A 读取 counter = 100
线程 B 读取 counter = 100   ← 读到同一个旧值
线程 A 写回 101
线程 B 写回 101             ← 两次自增，counter 只涨了 1
```

线程 A 和 B 各自读到相同的旧值，写回时彼此覆盖。做了两次工作，只得到一次结果。累加的次数越多，丢失的次数就越多，最终结果就越偏小。

好的，按照你的要求，把第3、4、5节中涉及的接口用表格形式整理出来，并保持内容简洁、前后连贯。

## 3. std::mutex

为了解决两个线程交错读取旧值的问题，C++ 提供了互斥锁 `std::mutex`。

`std::mutex` 用来把临界区串行化——同一时刻只允许一个线程进入受保护的代码段。拿到锁的线程执行临界区，其余线程在外面等，等前一个线程释放锁之后，下一个才能进去。这样就打破了"两个线程同时读到旧值"的情况：线程 A 持锁期间，线程 B 只能等 A 写完、释放锁之后才能进来读，读到的一定是 A 已经更新过的值。

`std::mutex` 的核心接口：

| 成员函数 | 作用 |
|----------|------|
| `lock()` | 加锁，如果锁已被占用则阻塞等待 |
| `unlock()` | 解锁，唤醒等待中的线程 |
| `try_lock()` | 尝试加锁，若锁可用则返回 true 并加锁，否则立即返回 false |

但手写 `lock()` / `unlock()` 有风险——如果临界区里抛了异常或者有 `return` 提前退出，`unlock()` 会被跳过，锁就永远不会释放，其他线程全部卡死。因此，实际开发中很少直接使用这两个接口，而是采用更安全的 RAII 封装。

## 4. std::lock_guard 与 std::unique_lock

`std::lock_guard` 是对 `std::mutex` 的 RAII 封装，解决了手动解锁容易遗漏的问题。构造时加锁，析构时自动解锁，无论以什么方式离开作用域——正常退出、`return`、异常——锁都一定会被释放。

`std::unique_lock` 更灵活，可以手动解锁、延迟加锁，常用于条件变量等场景。

接口对比如下：

| 类 | 主要成员函数 | 作用 |
|----|--------------|------|
| `std::lock_guard` | 构造函数（加锁）<br>析构函数（解锁） | 构造时加锁，析构时解锁，不可中途干预 |
| `std::unique_lock` | `lock()` / `unlock()`<br>`try_lock()`<br>`release()`（释放锁的所有权）<br>构造函数（支持 defer_lock, adopt_lock, try_to_lock） | RAII，但可手动解锁、转移所有权、延迟加锁 |

使用示例：
```cpp
void count_up_safe(int& c, std::mutex& m) {
    for (int i = 0; i < N; ++i) {
        std::lock_guard<std::mutex> lock(m);
        ++c;
    }
}
```

加上锁之后再运行，结果稳定正确：
```
result: 200000  (expected: 200000)
result: 200000  (expected: 200000)
```

总体来说，对于互斥锁的管理有如下的对比表格：
| 方式 | 特点 | 适用场景 |
|------|------|---------|
| `lock()` / `unlock()` | 手动管理，容易漏解锁 | 几乎不用 |
| `std::lock_guard` | RAII，作用域自动解锁，不可手动提前解锁 | 绝大多数情况 |
| `std::unique_lock` | RAII，但可以手动解锁、延迟加锁 | 条件变量、需要中途释放锁的场景 |

## 5. std::ref
使用 RAII 锁之后，还有一个细节容易踩坑：如何把变量和锁正确传递给线程？接下来就介绍 `std::thread` 的传参方式。

`std::thread` 默认按值传参——构造时把所有参数拷贝一份，启动线程时把拷贝传给目标函数。例如：
```cpp
void func(int a, int &b) { b = a + 1; }

int x = 10, y = 20;
std::thread t1(func, x, std::ref(y));
```

- 对于拷贝传参，如例子中的 `x` ，`func` 内部修改的是 `x` 的副本，不影响外部的 `x`
- 对于引用传参，如例子中的 `y` ，需要用 `std::ref` 包装，传的是真正的引用，函数内的修改会反映到外部的 `y`。

具体地说，`std::thread` 默认会**拷贝（或移动）** 所有传给它的参数。如果直接传 `counter`，得到的是副本，不是同一个变量。

为了解决这个问题，`std::ref` 返回一个 `std::reference_wrapper` 包装器，其内部只存有一个指针，可以被安全地拷贝。`std::thread` 拷贝这个包装器，然后在调用目标函数时，包装器自动转换成原始引用，从而让线程共享同一个变量。互斥锁 `mtx` 同理，必须通过 `std::ref` 传递，否则会尝试拷贝一个不可拷贝的 `std::mutex` 导致编译错误。

综上，如果想在线程间共享原始对象，需要用 `std::ref`（或 `std::cref` 传递 const 引用）包装，告诉 `std::thread` 不要拷贝，直接传原对象。对于只能移动不能拷贝的参数（如 `std::unique_ptr`），则需要用 `std::move` 转移所有权。

对于 `mtx` 也是同理——两个线程必须共享同一把锁，如果各自拿一把锁，互斥就完全没有效果了。这样，配合 `std::lock_guard` 和共享的 `std::mutex`，才能实现真正线程安全的累加。

## 6. 完整示例
```cpp
#include <iostream>
#include <thread>
#include <mutex>

const int N = 100000;

void count_up(int& c) {
    for (int i = 0; i < N; ++i)
        ++c;
}

void count_up_safe(int& c, std::mutex& m) {
    for (int i = 0; i < N; ++i) {
        std::lock_guard<std::mutex> lock(m);
        ++c;
    }
}

int main() {
    int counter = 0;
    {
        std::thread t1(count_up, std::ref(counter));
        std::thread t2(count_up, std::ref(counter));
        t1.join();
        t2.join();
        std::cout << "no lock:   " << counter << "  (expected " << 2 * N << ")\n";
    }

    counter = 0;
    {
        std::mutex mtx;
        std::thread t1(count_up_safe, std::ref(counter), std::ref(mtx));
        std::thread t2(count_up_safe, std::ref(counter), std::ref(mtx));
        t1.join();
        t2.join();
        std::cout << "with lock: " << counter << "  (expected " << 2 * N << ")\n";
    }
}
```

两段代码的差别只有一把锁。前者结果不定，后者稳定正确。一旦理解了 `counter++` 的三步拆解，这个结果就不再意外——多个线程同时改一个变量，没有互斥就没有正确性。
