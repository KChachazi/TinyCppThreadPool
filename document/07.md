# 07. 线程池 V2（生命周期管理）

V1 能提交任务、能拿结果、能在析构时干净退出。但它的"一生"是不完整的——它只认识"正在运行"这一种状态，对"我已经不接新活了"这件事没有任何表达能力。

这一节要补上的，就是线程池的生命周期：什么时候开始接任务、什么时候停止接、停止之后已经在排队的任务怎么办、外面想主动关掉它怎么办、关两次会不会出事。

## 1. V1 留下的坑：消失的任务

先看 V1 的 `submit()`：

```cpp
template <typename F>
auto submit(F task) -> std::future<std::invoke_result_t<F>> {
    using R = std::invoke_result_t<F>;
    auto pt = std::make_shared<std::packaged_task<R()>>(std::move(task));
    auto future = pt->get_future();
    queue_.push([pt]{ (*pt)(); });   // ← 返回值被丢掉了
    return future;
}
```

问题出在 `queue_.push(...)` 的返回值没人看。`BlockingQueue::push` 在队列已经 `stop()` 之后会返回 `ERROR_QUEUE_STOPPED`，并且**不入队**。于是这条链路就断了：

1. 任务没进队列，永远不会被执行。
2. `packaged_task` 没被调用，关联的 `future` 永远不会就绪。
3. 调用方拿着这个 `future` 调 `get()` —— 永久阻塞。

也就是说，V1 在线程池关闭后调 `submit()`，不是报错，而是**悄无声息地把调用方挂死**。这是比崩溃更难查的 bug。

V2 的第一件事，就是让 `submit()` 在这种情况下**明确失败**，而不是假装成功。

## 2. 一个明确的状态：Running / ShutDown

线程池只需要两个状态：

- **Running**：正常工作，接收新任务。
- **ShutDown**：不再接收新任务；队列里已有的任务继续跑完；所有 worker 跑完后退出。

注意 ShutDown 不是"立刻停"，而是"温和收尾"——已经排队的任务不丢。这一点其实第 5 章的 `BlockingQueue` 已经替我们实现了：`stop()` 之后 `pop()` 仍然会把队列里剩下的元素一个个交出去，直到队列空了才返回 `ERROR_QUEUE_STOPPED`。所以"排空再退出"是免费的，我们只要把状态切过去就行。

（如果要"立刻停、丢弃未执行的任务"那种语义——通常叫 `shutdownNow()`——需要给队列加一个清空操作。V2 先不做，留到后面。）

状态本身用一个 `std::atomic<bool> stopped_` 表示就够了。为什么是 `atomic` 而不是普通 `bool`：`submit()` 可能在任意线程被调用，`shutdown()` 可能在另一个线程被调用，两者会并发读写这个标志，普通 `bool` 上就是数据竞争。

## 3. submit() 必须会"拒绝"

改造后的 `submit()`：

```cpp
template <typename F>
auto submit(F task) -> std::future<std::invoke_result_t<F>> {
    using R = std::invoke_result_t<F>;
    auto pt = std::make_shared<std::packaged_task<R()>>(std::move(task));
    auto future = pt->get_future();
    if (queue_.push([pt]{ (*pt)(); }) != 0) {
        throw std::runtime_error("submit on stopped ThreadPool");
    }
    return future;
}
```

关键就是检查 `push()` 的返回值。这里有个值得说清楚的点：**判断"已关闭"这件事，交给 `queue_.push` 来做，而不是先读一下自己的 `stopped_` 再 push**。因为"读 `stopped_`"和"push"之间存在窗口——你读到 `false`，紧接着别的线程 `shutdown()` 了，你再 push 就 push 到一个已停的队列上。而 `BlockingQueue::push` 内部是"在同一把锁里检查 `stopped_` 并决定入不入队"，这个判断是原子的。所以让 push 的返回值当唯一裁判，就天然没有这个竞争。

`stopped_` 这个标志因此主要用于两件事：`shutdown()` 的幂等（见下一节）和对外提供一个 `isShutdown()` 查询；真正拦截 `submit` 的是 `push` 的返回码。当然，想给 `submit` 加一个 `if (stopped_.load()) throw ...` 的快速失败路径也行，但它只是优化，不能替代对 `push` 返回值的检查。

**为什么是 `throw`，不是返回一个无效的 `future`？** 默认构造的 `std::future` 是 "no state" 的，对它调 `get()` 会抛 `std::future_error`——但调用方在调 `get()` 之前根本不知道自己拿到的是个空壳，除非它每次都先 `valid()` 一下。在提交的那一刻直接抛异常，是 fail-fast：错误发生在它真正发生的地方，调用方想处理就 `try/catch`，不想处理就让它往上传，语义清清楚楚。（第 4 章 Demo 3 的那个最小任务队列就是这么做的。）

## 4. shutdown()：显式收尾，而且要幂等

V1 只能靠析构来关线程池。V2 给一个显式接口：

```cpp
void shutdown() {
    if (stopped_.exchange(true)) return;   // 已经关过了，直接返回
    queue_.stop();
    for (auto& w : workers_) {
        if (w.joinable()) w.join();
    }
}
```

两个点：

**幂等**。`shutdown()` 可能被调用多次（用户手动调一次，析构里再调一次），必须保证第二次及以后是空操作。`stopped_.exchange(true)` 返回的是**旧值**：第一个调用拿到 `false`，往下走真正去 `stop()` + `join()`；后续调用拿到 `true`，直接 return。如果不做这个保护，`std::thread::join()` 对一个已经 join 过的线程会抛 `std::system_error`——`if (w.joinable())` 那层判断能挡住二次 join 的崩溃，但不能阻止你对 `queue_` 重复 `stop()`（那个倒是无害），更重要的是不挡的话语义上就乱了。用 `exchange` 在最前面拦一道，干净。

**温和收尾**。`queue_.stop()` 只是把队列标记为停止，并 `notify_all()` 叫醒所有在 `pop()` 上等着的 worker。被叫醒的 worker 会发现队列里可能还有任务，于是继续 `pop()` 出来执行，直到队列真的空了，`pop()` 才返回非 0，`workerLoop` 退出。所以——**`shutdown()` 调用前已经成功进队列的任务，保证会被执行完**。这就是我们想要的"不丢任务"。

（一个边界：`shutdown()` 把 `stopped_` 设为 `true` 之后、`queue_.stop()` 执行之前，如果有别的线程 `submit()`，它的 `push` 可能还是成功的——因为队列还没 stop。这没问题：这个任务进了队列，就属于"已接收"，照样会被排空跑完。`stopped_` 和 `queue_` 的 stop 状态短暂不一致，但对外可见的不变量"已接收 ⟹ 会执行"始终成立。)

## 5. 析构和 shutdown() 的关系

有了幂等的 `shutdown()`，析构就一行：

```cpp
~ThreadPool() {
    shutdown();
}
```

不管用户之前有没有手动调过 `shutdown()`，析构里这一下都安全：调过了就是空操作，没调过就在这里把队列停掉、把线程 join 掉。线程池绝不能在还有 worker 没退出的情况下被销毁——那些 worker 还在访问 `queue_` 这个成员，对象一旦析构就是 use-after-free。所以析构里的 `join()` 是底线，`shutdown()` 帮我们把这个底线和"可显式调用"统一成了同一段逻辑。

顺序还是老规矩：先 `queue_.stop()`，再 `join()`。反过来——线程还在 `pop()` 里等任务，你先去 `join()` 它，就永远等下去了。

## 6. 这一节的接口设计目标

```cpp
class ThreadPool {
public:
    explicit ThreadPool(int numThreads);
    ~ThreadPool();

    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    template <typename F>
    auto submit(F task) -> std::future<std::invoke_result_t<F>>;

    void shutdown();                   // 幂等：停止接新任务，排空已有任务，等所有 worker 退出
    bool isShutdown() const noexcept;  // 查询当前是否已进入 ShutDown 状态

private:
    void workerLoop();

    BlockingQueue<std::function<void()>> queue_;
    myVector<std::thread> workers_;
    std::atomic<bool> stopped_{false};
};
```

相对 V1 的变化就三处：多了 `shutdown()` / `isShutdown()`，多了 `stopped_` 这个原子状态，`submit()` 会在队列已停时抛异常。其余（`submit` 的类型推导、类型擦除入队、`workerLoop` 靠 `pop` 返回非 0 退出、`workers_` 用 `myVector<std::thread>`）和 V1 完全一样。

## 7. 实践：把 V1 升级成 V2

直接在 `include/thread_pool.h` 上改。

实现前先想清楚：

1. `submit()` 里检查的是 `queue_.push()` 的返回值，而不是先读 `stopped_` 再 push——为什么后者有竞争？
2. `shutdown()` 开头用 `stopped_.exchange(true)` 而不是 `stopped_.store(true)`，差别在哪？换成 `if (stopped_) return; stopped_ = true;` 这种写法会有什么问题？
3. 析构里只调一个 `shutdown()` 够不够？如果用户在 `shutdown()` 之后又 `submit()` 了一个任务，会发生什么？

验证（对应 README 的"稳定性测试 (V2)"）：

- **关闭后提交会抛异常**：`shutdown()` 之后再 `submit()`，应该捕获到 `std::runtime_error`，而不是拿到一个永远卡住的 `future`。
- **不丢任务**：一个生产者线程疯狂 `submit()`（≥10 万次），主线程睡一会儿后 `shutdown()`。统计"`submit` 成功返回的次数"和"任务实际执行的次数"（任务里对一个 `std::atomic<int>` 自增），两者必须相等——已接收的一个都不能少。`shutdown()` 之后那些抛异常的 `submit` 不计入"已接收"。
- **不崩溃、不卡死**：整个过程跑完，程序正常退出。
- **幂等**：连着调两次 `shutdown()`，第二次什么都不做，不抛、不崩。

## 8. 完整实现参考

```cpp
#pragma once

#include <thread>
#include <future>
#include <functional>
#include <memory>
#include <atomic>
#include <stdexcept>

#include "blocking_queue.h"
#include "myVector.h"

class ThreadPool {
public:
    explicit ThreadPool(int numThreads) {
        workers_.reserve(numThreads);
        for (int i = 0; i < numThreads; i++) {
            workers_.emplace_back(&ThreadPool::workerLoop, this);
        }
    }

    ~ThreadPool() {
        shutdown();
    }

    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    template <typename F>
    auto submit(F task) -> std::future<std::invoke_result_t<F>> {
        using R = std::invoke_result_t<F>;
        auto pt = std::make_shared<std::packaged_task<R()>>(std::move(task));
        auto future = pt->get_future();
        if (queue_.push([pt]{ (*pt)(); }) != 0) {
            throw std::runtime_error("submit on stopped ThreadPool");
        }
        return future;
    }

    void shutdown() {
        if (stopped_.exchange(true)) return;
        queue_.stop();
        for (auto& w : workers_) {
            if (w.joinable()) w.join();
        }
    }

    bool isShutdown() const noexcept {
        return stopped_.load();
    }

private:
    void workerLoop() {
        std::function<void()> task;
        while (queue_.pop(task) == 0) {
            task();
        }
    }

    BlockingQueue<std::function<void()>> queue_;
    myVector<std::thread> workers_;
    std::atomic<bool> stopped_{false};
};
```

稳定性测试的骨架：

```cpp
#include "thread_pool.h"
#include <atomic>
#include <iostream>

int main() {
    std::atomic<int> executed{0};
    int accepted = 0;
    int rejected = 0;

    {
        ThreadPool pool(4);

        // 关闭后提交：应当抛异常
        pool.shutdown();
        try {
            pool.submit([]{ return 1; });
        } catch (const std::exception& e) {
            std::cout << "rejected as expected: " << e.what() << std::endl;
        }
    }

    {
        ThreadPool pool(4);
        std::thread flooder([&]{
            for (int i = 0; i < 200000; i++) {
                try {
                    pool.submit([&executed]{ executed.fetch_add(1, std::memory_order_relaxed); });
                    accepted++;
                } catch (const std::exception&) {
                    rejected++;
                }
            }
        });
        std::this_thread::sleep_for(std::chrono::milliseconds(20));
        pool.shutdown();   // 中途关闭
        pool.shutdown();   // 再来一次，验证幂等
        flooder.join();
        // pool 析构：再 shutdown 一次也无害
    }

    std::cout << "accepted=" << accepted
              << " rejected=" << rejected
              << " executed=" << executed.load()
              << (accepted == executed.load() ? "  (no task lost)" : "  (TASK LOST!)")
              << std::endl;
}
```

## 9. 小结

V2 把线程池的生命周期补完整了：它现在有明确的 Running / ShutDown 两态，`submit()` 在关闭后会明确拒绝而不是挂死调用方，`shutdown()` 是个幂等的显式接口，析构和它共用同一段收尾逻辑，并且关闭时不丢已接收的任务。

它还不够"工程化"的地方：固定的线程数、`shutdown()` 只有"温和排空"一种语义没有"立刻丢弃"、`submit` 抛异常之外没有更细的错误分类、没有任何对任务执行本身抛异常的处理、队列无界。下一节 V3 就来收拾这些工程化的细节。
