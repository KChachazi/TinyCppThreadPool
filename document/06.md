# 06. 线程池 V1（基础可用）

到这里，前五节的准备工作已经全部到位：线程生命周期、数据竞争、锁、任务抽象、阻塞队列。这一节把它们组合起来，实现第一个真正可用的线程池。

V1 的目标只有一个：**能提交任务，能拿到结果，能干净关闭**。不追求性能极致，不处理边界奇案，先把主干跑通。

## 1. 线程池的结构

线程池本质上是两个东西的组合：

- **一个任务队列**：接收外部提交的任务，缓存起来等待执行。
- **一组工作线程**：不断从队列里取任务、执行，直到被关闭。

提交任务的一方不需要知道哪个线程会执行它，只需要拿到一个 `future`，等结果就行。

```
submit(task) → future
     ↓
  BlockingQueue
     ↓
worker1 / worker2 / worker3 ... → 执行任务，结果写入 future
```

## 2. submit() 的类型问题

这是 V1 里最需要想清楚的一处设计。

我希望 `submit()` 能接受任意可调用对象，并返回对应类型的 `future`。比如：

```cpp
auto f1 = pool.submit([]{ return 42; });          // future<int>
auto f2 = pool.submit([]{ return 3.14; });        // future<double>
auto f3 = pool.submit([]{ return std::string{"hi"}; }); // future<string>
```

不同任务的返回类型不同，`submit()` 的返回类型也应该跟着变。这要用到函数模板，并且需要在编译期推导出任务的返回类型。

C++11 之后有 `std::result_of`，C++17 之后更推荐用 `std::invoke_result`，它们的作用是：给定一个可调用类型，告诉我调用它之后的返回类型是什么。

```cpp
template <typename F>
auto submit(F task) -> std::future<std::invoke_result_t<F>>;
```

`std::invoke_result_t<F>` 就是 `F` 被调用之后的返回类型。

## 3. 队列里存什么

`submit()` 收到的任务类型五花八门，但队列只能存一种类型。

解决方式是**类型擦除**：用 `packaged_task` 把任务包装好，再把它包进一个 `std::function<void()>` 存入队列。工作线程从队列里取出来直接 `task()` 执行，不需要知道原始任务的返回类型。

```cpp
template <typename F>
auto submit(F f) -> std::future<std::invoke_result_t<F>> {
    using R = std::invoke_result_t<F>;
    auto task = std::make_shared<std::packaged_task<R()>>(std::move(f));
    auto future = task->get_future();
    queue_.push([task]{ (*task)(); });
    return future;
}
```

这里用 `shared_ptr` 包装 `packaged_task` 是因为：`packaged_task` 不可复制，而 `std::function` 内部需要可复制的捕获——用 `shared_ptr` 让 lambda 捕获一个可复制的指针，就绕开了这个限制。

## 4. 工作线程的逻辑

每个工作线程的逻辑很简单：

```cpp
void workerLoop() {
    std::function<void()> task;
    while (queue_.pop(task)) {
        task();
    }
}
```

`pop()` 返回 `false` 时说明队列已关闭，线程自然退出。这正是上一节阻塞队列的价值所在：调用方的退出逻辑完全不需要额外的退出标志。

## 5. 构造与析构

线程池在构造时启动工作线程，在析构时关闭队列并等待所有线程退出：

```cpp
ThreadPool(int numThreads) {
    for (int i = 0; i < numThreads; i++) {
        workers_.emplace_back([this]{ workerLoop(); });
    }
}

~ThreadPool() {
    queue_.stop();
    for (auto& t : workers_) t.join();
}
```

析构里先 `stop()` 再 `join()`，顺序不能反。`stop()` 通知队列关闭，`join()` 等每个线程真正退出。如果先 `join()` 再 `stop()`，线程还在等任务，`join()` 会永远卡住。

顺带一提，`workers_` 这里用的是项目里自己实现的 `myVector<std::thread>`，不是 `std::vector`——能复用自己写的轮子就复用。`std::thread` 是 move-only 类型，`myVector` 扩容搬迁时会走移动构造（它对非 trivially-copyable 类型用 `move_if_noexcept`，而 `std::thread` 的移动构造是 `noexcept` 的），所以这个替换不会有任何副作用。想省掉那几次扩容搬迁的话，构造时可以先 `workers_.reserve(numThreads)`。

## 6. 这一节的接口设计目标

```cpp
class ThreadPool {
public:
    explicit ThreadPool(int numThreads);
    ~ThreadPool();

    template <typename F>
    auto submit(F task) -> std::future<std::invoke_result_t<F>>;

private:
    void workerLoop();

    BlockingQueue<std::function<void()>> queue_;
    myVector<std::thread> workers_;
};
```

注意几点：
- 构造函数用 `explicit` 防止隐式转换（`ThreadPool pool = 4` 这种写法不应该合法）。
- 线程池不应该被复制，所以把拷贝构造和赋值运算符 `= delete` 掉。
- `submit()` 是模板成员函数，实现必须放在头文件里。
- 工作线程容器用 `myVector<std::thread>`，需要 `#include "myVector.h"`。

## 7. 实践：实现 ThreadPool V1

你需要新建 `include/thread_pool.h`，实现上面这个类。

实现前先想清楚这几个问题：

1. `submit()` 里为什么要用 `shared_ptr<packaged_task>`，而不是直接 move 进 lambda？
2. 构造时 `emplace_back` 和 `push_back` 在这里有什么区别？
3. 析构时如果用户已经手动调过 `stop()`，再次调用会不会有问题？（看看 `BlockingQueue::stop()` 的实现）

验证方式：提交若干个有返回值的任务，用 `future.get()` 等结果，观察是否正确返回，且所有线程在析构时能干净退出。

## 8. 完整实现参考

```cpp
#pragma once

#include <thread>
#include <future>
#include <functional>
#include <memory>

#include "blocking_queue.h"
#include "myVector.h"

class ThreadPool {
public:
    explicit ThreadPool(int numThreads) {
        workers_.reserve(numThreads);
        for (int i = 0; i < numThreads; i++) {
            workers_.emplace_back([this]{ workerLoop(); });
        }
    }

    ~ThreadPool() {
        queue_.stop();
        for (auto& t : workers_) t.join();
    }

    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    template <typename F>
    auto submit(F task) -> std::future<std::invoke_result_t<F>> {
        using R = std::invoke_result_t<F>;
        auto pt = std::make_shared<std::packaged_task<R()>>(std::move(task));
        auto future = pt->get_future();
        queue_.push([pt]{ (*pt)(); });
        return future;
    }

private:
    void workerLoop() {
        std::function<void()> task;
        while (queue_.pop(task) == 0) {
            task();
        }
    }

    BlockingQueue<std::function<void()>> queue_;
    myVector<std::thread> workers_;
};
```

测试程序示例：

```cpp
#include "thread_pool.h"
#include <iostream>

int main() {
    ThreadPool pool(4);

    auto f1 = pool.submit([]{ return 1 + 1; });
    auto f2 = pool.submit([]{ return std::string("hello"); });
    auto f3 = pool.submit([]{
        std::this_thread::sleep_for(std::chrono::milliseconds(100));
        return 3.14;
    });

    std::cout << f1.get() << std::endl;
    std::cout << f2.get() << std::endl;
    std::cout << f3.get() << std::endl;
}
```

## 9. 小结

V1 的线程池已经具备了最核心的三个能力：提交任务、返回结果、干净关闭。

它目前的局限是：没有任何对"提交到已关闭的线程池"的保护，`submit()` 在 `stop()` 之后调用会静默丢任务（`push()` 返回非 0，但 `submit()` 不检查）。这个问题留给 V2 处理。

下一节 V2 会在这个基础上加入完整的生命周期管理：能安全处理关闭后提交、支持显式 `shutdown()` 接口、以及更健壮的错误返回。
