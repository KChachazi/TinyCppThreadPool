# 锁的工程化使用与死锁规避

上一篇用一把 `std::mutex` 修好了数据竞争——加锁之后，`counter++` 的结果稳定回到了 200000。通过引入互斥锁，我们解决了共享数据在线程协作中的数据竞争问题。

但锁本身也会带来新的麻烦，**加了锁，不意味着一定安全**。当我们使用多个锁的时候，就会出现最典型的反例，死锁——程序卡死，永远不动。

所以首先，来看一段代码，观察死锁的产生。

## 0. 实验：死锁
在下面这份代码里，两把锁 `m1`、`m2`，两个线程，各自都要把两把锁都拿到手才能干活：
```cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <chrono>

std::mutex m1, m2;

void thread_A() {
    std::lock_guard<std::mutex> lock1(m1);          // 先拿 m1
    std::cout << "A 拿到 m1，准备拿 m2\n";
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::lock_guard<std::mutex> lock2(m2);          // 再拿 m2
    std::cout << "A 拿到了两把锁\n";
}

void thread_B() {
    std::lock_guard<std::mutex> lock2(m2);          // 先拿 m2
    std::cout << "B 拿到 m2，准备拿 m1\n";
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::lock_guard<std::mutex> lock1(m1);          // 再拿 m1
    std::cout << "B 拿到了两把锁\n";
}

int main() {
    std::thread t1(thread_A);
    std::thread t2(thread_B);
    t1.join();
    t2.join();
    std::cout << "main done\n";
}
```

两个函数的逻辑几乎一样，唯一的区别是加锁顺序相反：`thread_A` 先 `m1` 后 `m2`，`thread_B` 先 `m2` 后 `m1`。运行它，输出通常停在这里：

```
A 拿到 m1，准备拿 m2
B 拿到 m2，准备拿 m1
```

然后程序就再也不动了。`A 拿到了两把锁` 不会打印，`main done` 也不会打印，`join()` 永远返回不了。这不是跑得慢，是真的卡死——这就是死锁。

中间那句 `sleep_for` 不是必须的，它的作用是让死锁**稳定复现**：强行制造一个时间窗口，让两个线程都先拿到各自的第一把锁，再去抢第二把。没有它，死锁也会发生，只是要靠调度时机正好撞上，可能跑很多次才出现一次。

## 1. 死锁是什么

死锁是指：两个或多个线程互相等待对方持有的锁，结果谁都没法继续往下走。

回到上面的例子，卡住的那一刻，现场是这样的：
```
线程 A 持有 m1，正在等 m2
线程 B 持有 m2，正在等 m1
```

A 要的 `m2` 在 B 手里，B 要的 `m1` 在 A 手里。A 在等 B 放手，B 在等 A 放手，而锁只能由持有者主动释放——于是形成一个闭环，谁也不会先松手。这个闭环就是死锁的本质：**一条首尾相接的等待链**。

学术上，死锁的出现要同时满足四个条件（Coffman 条件）：
- **互斥**：锁同一时刻只能被一个线程持有。
- **持有并等待**：线程拿着一把锁的同时，又去申请另一把。
- **不可剥夺**：锁不能被强行抢走，只能由持有者释放。
- **循环等待**：存在一条线程互相等待的环。

前三个几乎是「用锁」这件事自带的，很难绕开。真正能由我们控制、也最该下手的，是第四个——只要打破循环等待，死锁就不会发生。后面讲的修复方法，本质都是在拆这个环。

## 2. 死锁是怎么发生的
死锁最常见的来源不是单独一把锁，而是**多把锁，加锁顺序不一致**。

我们来拆分第 0 节出现死锁导致卡死的时间线：
```
时刻 1   线程 A: 拿到 m1
时刻 2   线程 B: 拿到 m2
时刻 3   线程 A: 想拿 m2 → m2 在 B 手里 → A 阻塞
时刻 4   线程 B: 想拿 m1 → m1 在 A 手里 → B 阻塞
此后     两个线程都在等对方，永远等下去
```

关键在时刻 3 和 4：两个线程都已经持有一把锁，又都在等另一把。只要两条线程拿锁的顺序相反，并且时机正好撞上（都拿完第一把、还没拿第二把），环就闭合了。

值得注意的是，**这段代码每一行单独看都没错**。`lock_guard` 用得很标准，临界区也不会忘记解锁。死锁不是某一行的 bug，而是多个线程的加锁顺序在全局上凑成了一个环。

因此，死锁是结构性问题，不是语法问题。

除了「多锁不同序」，还有几个容易踩的典型场景：

- **重复锁同一把锁**：`std::mutex` 不可重入。同一个线程对自己已经持有的 `mutex` 再 `lock()` 一次，就会卡死自己（标准上属于未定义行为，多数实现表现为死锁）。这种情况常出现在「一个持锁的函数，又调用了另一个也要锁同一把锁的函数」。
- **持锁调用外部代码**：在持有锁的时候调用回调、虚函数或别人写的函数，而那段代码内部又去拿别的锁——你无法控制它的加锁顺序，等于把环交给了别人去闭合。

这一篇聚焦最核心的「多锁不同序」——它最经典的真实形态就是银行转账（第 4 节），后面的修复和实例都围绕它展开。

## 3. 修复死锁

修复死锁的目标只有一个：拆掉那个等待环。动手之前，先把工具摆出来。

上一篇已经用过 `std::lock_guard` 和 `std::unique_lock`——构造时加锁，析构时自动解锁，临界区无论怎么退出都不会漏掉 `unlock()`。它们解决的是「单把锁」的安全问题。到了多把锁的场景，C++17 又补了一个 `std::scoped_lock`。三者的分工大致是：

| 类 | 管理的锁 | 特点 | 典型场景 |
|----|---------|------|---------|
| `std::lock_guard` | 单把 | 构造加锁、析构解锁，不能中途干预 | 绝大多数单锁临界区 |
| `std::unique_lock` | 单把 | RAII，但可手动解锁、延迟加锁、转移所有权 | 条件变量、需要中途放锁 |
| `std::scoped_lock` | 一把或多把 | 多把锁一次性锁定，自带死锁避免 | 需要同时持有多把锁 |

下面三种修复做法，本质都是借这些 RAII 锁去拆掉等待环。

### 3.1 一致加锁顺序

最朴素的办法：约定一个全局的加锁顺序，所有线程都按这个顺序拿锁。只要永远「先 `m1` 后 `m2`」，两条线程就不可能一个持 `m1` 等 `m2`、另一个持 `m2` 等 `m1`，环自然闭不上——这正是直接打破第 1 节四个条件里的「循环等待」。

```cpp
void thread_A() {
    std::lock_guard<std::mutex> l1(m1);   // 先 m1
    std::lock_guard<std::mutex> l2(m2);   // 后 m2
}
void thread_B() {
    std::lock_guard<std::mutex> l1(m1);   // 和 A 完全相同的顺序
    std::lock_guard<std::mutex> l2(m2);
}
```

这招的麻烦在于：真实代码里加锁顺序往往是**动态**的。比如转账函数 `transfer(from, to)`，`from` 和 `to` 是参数，到底先锁哪个、编译期并不知道。这时得靠一个稳定的排序键来定序，比如对象地址：

```cpp
// 总是先锁地址较小的那个
std::mutex* first  = (&a < &b) ? &a : &b;
std::mutex* second = (&a < &b) ? &b : &a;
std::lock_guard<std::mutex> l1(*first);
std::lock_guard<std::mutex> l2(*second);
```

这种方法的确能用，但很啰嗦，而且容易写错。

### 3.2 一次性锁定多把锁（std::scoped_lock）

更省心的办法是把多把锁交给 `scoped_lock` 一次性锁定。它和 `lock_guard` 一样是「构造即加锁、析构即解锁」，区别在于它能一次接收多把 `mutex`：

```cpp
std::scoped_lock lock(m1, m2);   // 同时锁住 m1 和 m2
```

`scoped_lock` 不是简单地执行先锁 m1 再锁 m2，这样是无法避免死锁的。其内部用的是一套死锁避免算法，整个过程是这样一个循环：

```
反复执行：
    阻塞地锁住第一把锁           ← 此刻线程手上没有任何别的锁
    其余每把锁逐个 try_lock      ← try_lock 不阻塞，拿不到就立刻返回失败
    全部拿到  → 成功，退出循环
    没拿全    → 把已拿到的锁全部松开，回到开头重试
```

关键在 `try_lock`：它和 `lock` 不同，拿不到锁时不会阻塞等待，而是立刻返回失败。于是整个算法里，**唯一会「阻塞等待」的动作，只发生在线程手上一把锁都没有的时候**；一旦已经持有了锁，后面就只做不阻塞的尝试，一旦拿不全就立即全部松手。

这样一来，线程永远不会停在「持有并等待」的状态中——这是直接打破四个条件里的另一个。加锁顺序怎么写也都无所谓，`scoped_lock(m1, m2)` 和 `scoped_lock(m2, m1)` 完全等价，循环等待的环根本组不起来。第 0 节的死锁，把两个函数里的两句 `lock_guard` 换成一句 `scoped_lock`，就彻底修好了。

### 3.3 一次性锁定多把锁（unique_lock + defer_lock + std::lock）

如果需要先把锁对象构造出来、过一会儿再加锁（比如要和条件变量配合），可以用 `defer_lock` 让 `unique_lock` 先不加锁，之后再用 `std::lock` 一次性锁定：

```cpp
std::unique_lock<std::mutex> l1(m1, std::defer_lock);
std::unique_lock<std::mutex> l2(m2, std::defer_lock);
std::lock(l1, l2);   // 和 scoped_lock 同一套死锁避免算法
```

`std::lock` 和 `scoped_lock` 用的是同一套算法，效果一致。区别只是 `scoped_lock` 把「构造 + 加锁」合成了一步，而 `defer_lock` 这套把两步拆开，换来对加锁时机的控制权。

## 4. 工程实例：银行转账

接下来把上面的技巧放进一个更接近真实的场景：多个线程在两个银行账户之间反复转账。

### 4.1 需求

模拟一个多线程的银行转账程序：

- 有两个账户，初始各有一笔余额。
- 多个工作线程并发地在两个账户之间转账，每笔转账的金额和方向都随机。
- 另有一个监控线程，定期对两个账户做一次余额快照，打印当前总额。

正确性上要满足三条：

- **不死锁**：转账线程之间、转账线程和监控线程之间，并发抢锁都不能把程序卡住。
- **不串账**：一笔转账「从 A 扣钱、给 B 加钱」必须原子完成，别的线程不能看到「钱已扣、还没到账」的中间状态。
- **总额守恒**：转账只是搬钱，跑完之后两个账户的余额之和必须和初始时完全相等。

### 4.2 设计

先定锁的归属：**每个账户自带一把锁**，谁要碰这个账户的余额，就得先拿它的锁。

转账要同时改两个账户——从 `from` 扣钱、给 `to` 加钱。要让这两步对外表现为一个原子操作、不被别人看到中间状态，转账线程就必须**同时持有**两个账户的锁，全程不松手。

顺着这个思路，很自然会写出依次锁两把的代码：
```cpp
// 危险写法：依次加锁，顺序由参数决定
void transfer(BankAccount& from, BankAccount& to, double amount) {
    lock_guard<mutex> l1(from.AcquireLock());
    lock_guard<mutex> l2(to.AcquireLock());
    // ...
}
```

但这正是第 0 节那段死锁代码的真实版本。当一个线程跑 `transfer(account1, account2)`、另一个线程跑 `transfer(account2, account1)`，两者的加锁顺序正好相反：一个先锁 `account1`，一个先锁 `account2`——循环等待出现了。而程序里有 10 个线程随机选方向转账，反向撞上几乎是必然的。

所以转账必须用第 3 节的办法一次锁两把。程序里有两个角色都要同时持有这两把账户锁，分别用两种等价写法：
- **转账线程**：一进函数就要两把锁、作用域固定——用 `scoped_lock`。
- **监控线程**：做快照同样要两把锁，否则可能读到一个账户转账前、另一个转账后的不一致总额——用 `defer_lock` + `std::lock`。

两者底层是同一套死锁避免算法，所以即使转账和快照并发抢同样两把锁，也不会形成环。

最后是收尾：监控线程是个「不停做快照」的循环，必须有人显式叫停。设计上让它盯着一个 `atomic<bool>` 停止标志——主线程等所有转账线程 `join` 完之后，再把标志置位、`join` 掉监控线程。

### 4.3 实现

**账户类**。余额配一把锁；`Deposit` / `Withdraw` 这两个方法本身不管理锁，必须由调用者在调用前持有当前账户的 mtx 锁。

```cpp
class BankAccount {
private:
    string accountHolder;
    double balance;
    mutex mtx;
public:
    BankAccount(const string& holder, double initialBalance)
        : accountHolder(holder), balance(initialBalance) {}

    mutex& AcquireLock() { return mtx; }
    double GetBalance() const { return balance; }
    const std::string& GetAccountHolder() const { return accountHolder; }

    bool Deposit(double amount) {
        if (amount < 0) return false;
        balance += amount;
        return true;
    }
    bool Withdraw(double amount) {
        if (amount < 0 || amount > balance) return false;
        balance -= amount;
        return true;
    }
};

BankAccount account1("Alice", 1000);
BankAccount account2("Bob", 500);
```

**转账**。`scoped_lock` 一次锁两把，锁住期间完成扣款和入账。

```cpp
void transfer(BankAccount& from, BankAccount& to, double amount) {
    scoped_lock lock(from.AcquireLock(), to.AcquireLock());

    if (from.Withdraw(amount)) {
        to.Deposit(amount);
        cout << "Transferred " << amount << " from "
             << from.GetAccountHolder() << " to "
             << to.GetAccountHolder() << "." << endl;
    } else {
        cout << "Failed to transfer " << amount << " ..." << endl;
    }
}
```

**监控快照**。换 `defer_lock` + `std::lock` 的写法，作用和 `scoped_lock` 一样。在函数 `MonitorTask` 中使用原子量进行终止。

```cpp
void SnapshotTotal() {
    unique_lock<mutex> lock1(account1.AcquireLock(), defer_lock);
    unique_lock<mutex> lock2(account2.AcquireLock(), defer_lock);

    std::lock(lock1, lock2);   // 一次性锁定两把，避免死锁

    double total = account1.GetBalance() + account2.GetBalance();
    cout << "Total balance: " << total << endl;
}

void MonitorTask(atomic<bool>& stopRequested) {
    while (!stopRequested.load()) {
        this_thread::sleep_for(chrono::milliseconds(20));
        SnapshotTotal();
    }
}
```

**驱动**。建线程、`join`，注意收尾顺序。

```cpp
int main() {
    atomic<bool> stopMonitor(false);
    thread monitor(MonitorTask, ref(stopMonitor));

    thread threads[TOTAL_THREADS];
    for (int i = 0; i < TOTAL_THREADS; ++i)
        threads[i] = thread([&]() { /* 随机方向转账 100 次 */ });

    for (int i = 0; i < TOTAL_THREADS; ++i)
        threads[i].join();

    stopMonitor.store(true);   // 工作线程结束后再停监控
    monitor.join();
}
```

先 `join` 所有转账线程，再用 `stopMonitor` 通知监控线程退出、最后 `join` 它——监控线程的 `while (!stop)` 循环必须有人显式叫停，否则它会一直转下去。这和第 01 篇说的「每个 joinable 线程都得有人收尾」是同一件事。

程序跑完后，两个账户的余额之和恒等于初始的 1500——总额守恒，说明每一笔转账都原子地完成了，4.1 列的三条要求全部满足。

## 5. 小结

死锁和数据竞争是并发的两类基本问题。为了解决数据竞争，我们引入的互斥锁；单个互斥锁在正确使用（不重复锁定、不忘记解锁）的前提下不会自行产生死锁，但是多个互斥锁的获取可能会相互卡死，这就是死锁；通过打破锁的持有状态，或者环形依赖，我们可以解决死锁的问题。

有关死锁，最反直觉的一点是：它不是任何单独一行代码的错误。每一句 `lock` 都合法，临界区也都规范，问题出在多个线程的加锁顺序在全局上闭合成了环。所以修复也得是结构性的——要么统一加锁顺序，要么用 `scoped_lock` / `std::lock` 一次锁多把，让线程永远不处于「持有一把、等待另一把」的状态。
