# 05. 阻塞队列设计

上一节做了一个最小任务队列（Demo 3），它能把任务存起来、让工作线程取出来执行，也有基本的关闭信号。但它只是一个内嵌在 `TaskQueue` 类里的私有实现，不够通用，也没法直接复用到后面的线程池里。

这一节的目标，就是把"阻塞队列"这个能力单独抽出来，设计成一个干净的、可复用的组件。

## 1. 为什么要单独设计阻塞队列

线程池的核心结构可以粗略拆成两半：

- **队列**：负责存任务、取任务，协调生产者和消费者。
- **线程管理**：负责维护工作线程的生命周期，从队列里取任务执行。

如果这两部分混在一起，代码很快就会变得难以修改。队列的并发逻辑和线程的调度逻辑互相缠绕，改一个容易破坏另一个。

所以先把队列单独做好，是有价值的。线程池在上面组合就行，不需要再操心队列内部的锁和条件变量。

## 2. 阻塞队列需要解决的三个问题

一个给线程池用的队列，最基本的要求有三条：

**队列空时，取操作要等，而不是立即返回空或报错。**

这就是"阻塞"的意义。工作线程不能闲置地轮询，必须在有任务到来时才被唤醒。这靠条件变量实现，不靠忙等。

**关闭队列时，等待中的线程要能安全退出。**

如果线程在 `cv.wait()` 里等任务，而队列关闭时不做任何通知，线程会永远卡住。关闭信号必须能打破这个等待。

**`pop()` 的返回值要能区分两种情况：取到任务，还是队列已关闭。**

这两种情况对调用者来说意义完全不同。如果混在一起或者靠异常处理，工作线程的逻辑会变得复杂。

## 3. 条件变量的 predicate 怎么写

在 03、04 节里已经用过条件变量了。这里再强调一次在阻塞队列里最容易写错的地方。

`cv.wait(lock, predicate)` 的语义是：

- 先检查 predicate，如果为 true，直接继续。
- 如果为 false，释放锁，进入等待，被唤醒后重新检查 predicate。

阻塞队列的 `pop()` 应该等待的条件是：**队列非空，或者队列已经关闭**。

如果只等"队列非空"，关闭信号就没法打破等待——线程会一直挂着。

```cpp
cv.wait(lock, [this] {
    return !queue_.empty() || stopped_;
});
```

唤醒后还需要判断到底是哪种情况触发的：

```cpp
if (stopped_ && queue_.empty()) {
    return false;  // 队列关闭且无任务，通知调用者退出
}
```

这个顺序很重要。先检查是否有任务，再检查是否关闭，还是先关闭再取任务——这背后藏着一个设计决策：**关闭时，队列里还有的任务要不要继续处理？**

两种策略各有场景：

- **drain-on-close**：关闭后继续取完剩余任务，再退出。适合任务不能丢的场景。
- **abort-on-close**：关闭后立即停，不管队列里还有什么。适合需要快速响应停止信号的场景。

这一节先用 drain-on-close，因为它和线程池的正常关闭语义一致。

## 4. `pop()` 的返回值设计

最常见的两种写法：

**方式一：bool + 引用参数**

```cpp
bool pop(T& item);
```

返回 `false` 代表队列关闭，调用方收到信号后退出循环。返回 `true` 代表取到了任务，`item` 里有值。

**方式二：`std::optional<T>`**

```cpp
std::optional<T> pop();
```

返回空的 `optional` 代表关闭，返回有值的 `optional` 代表取到了任务。

两种写法都可以，各有取舍：

| | bool + ref | optional |
|---|---|---|
| 语义清晰度 | 返回值只表示状态，值通过 ref 给出 | 返回值同时携带状态和值 |
| 使用场景限制 | `T` 必须是可默认构造的（ref 要先声明变量） | 无此限制 |
| C++ 版本要求 | C++11 | C++17 |
| 调用方写法 | `T item; if (q.pop(item)) { ... }` | `if (auto item = q.pop()) { ... }` |

线程池里的任务类型 `std::function<void()>` 是可默认构造的，两种写法都可以用。这一节选 bool + ref，主要是想让返回值的语义更显眼——`false` 就是"退出"，不需要解包。

## 5. 模板化的意义

阻塞队列本身不需要知道里面存的是什么任务。它只关心：能存、能取、能关闭。

用模板实现可以让这个队列在不同场景下复用：存 `std::function<void()>`、存 `packaged_task`、或者存任意其他类型都没问题。

```cpp
template<typename T>
class BlockingQueue { ... };
```

不过模板类的实现必须放在头文件里（或者 `.h` + 显式实例化），不能像普通类一样分 `.h` / `.cpp`。这是一个常见的新手坑。

## 6. 一个关键的移动语义细节

`std::packaged_task` 和 `std::function` 都是**只可移动，不可复制**的类型（前者）或者**可复制但移动更高效**的类型（后者）。

从队列里取任务时，应该用 `std::move`：

```cpp
item = std::move(queue_.front());
queue_.pop();
```

如果写成 `item = queue_.front()`，某些类型会报编译错误，某些类型会引发不必要的复制。

## 7. 实践：实现 BlockingQueue

在这一节里，你需要实现一个 `BlockingQueue<T>`，接口如下：

```cpp
template<typename T>
class BlockingQueue {
public:
    void push(T item);
    bool pop(T& item);   // 返回 false 表示队列已关闭，调用方应退出
    void stop();         // 关闭队列，唤醒所有等待中的线程

private:
    std::queue<T> queue_;
    std::mutex mtx_;
    std::condition_variable cv_;
    bool stopped_ = false;
};
```

验证它的方式，是用这个队列替换掉 04 节 Demo 3 里的内嵌实现，行为应该完全一致。

## 8. 完整实现参考

```cpp
#include <iostream>
#include <queue>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <functional>

template<typename T>
class BlockingQueue {
public:
    void push(T item) {
        {
            std::lock_guard<std::mutex> lock(mtx_);
            if (stopped_) return;
            queue_.push(std::move(item));
        }
        cv_.notify_one();
    }

    bool pop(T& item) {
        std::unique_lock<std::mutex> lock(mtx_);
        cv_.wait(lock, [this] {
            return !queue_.empty() || stopped_;
        });
        if (queue_.empty()) return false;
        item = std::move(queue_.front());
        queue_.pop();
        return true;
    }

    void stop() {
        {
            std::lock_guard<std::mutex> lock(mtx_);
            stopped_ = true;
        }
        cv_.notify_all();
    }

private:
    std::queue<T> queue_;
    std::mutex mtx_;
    std::condition_variable cv_;
    bool stopped_ = false;
};

int main() {
    BlockingQueue<std::function<void()>> queue;

    std::thread worker([&queue] {
        std::function<void()> task;
        while (queue.pop(task)) {
            task();
        }
        std::cout << "Worker exited cleanly." << std::endl;
    });

    queue.push([] { std::cout << "Task 1 done." << std::endl; });
    queue.push([] { std::cout << "Task 2 done." << std::endl; });
    queue.push([] { std::cout << "Task 3 done." << std::endl; });

    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    queue.stop();
    worker.join();

    return 0;
}
```

**输出**：

```
Task 1 done.
Task 2 done.
Task 3 done.
Worker exited cleanly.
```

工作线程通过 `while (queue.pop(task))` 驱动整个循环，`pop()` 返回 `false` 时自然退出，不需要任何额外的退出标志。这是阻塞队列设计带来的最直接的好处：调用方的循环结构极为简洁。

## 9. 几个值得自己试一试的边界情况

- **stop() 之后再 push()**：现在的实现是直接 return，任务静默丢弃。如果你想让调用方知道 push 失败了，应该怎么改？（提示：改 push 的返回值）
- **多个工作线程**：把 worker 改成多个线程，队列是否还能正常工作？`notify_one` 和 `notify_all` 在这里各有什么影响？
- **drain-on-close 的验证**：在 `stop()` 之前 push 大量任务，观察是否所有任务都会被处理完再退出。

## 10. 小结

阻塞队列是线程池的核心数据结构。把它单独设计好之后，下一节的线程池 V1 就只需要在上面组合工作线程和任务提交接口，不需要再操心并发细节。

这一节最值得记住的两点：

1. `pop()` 的 predicate 必须同时覆盖"有任务"和"已关闭"两种情况。
2. `pop()` 的返回值要能让调用方区分"取到任务"和"应该退出"。

这两点如果没做对，工作线程要么卡死，要么退出逻辑变成一坨 if。
