# 08. 线程池 V3（工程优化）

V2 把生命周期补完了，但离「工程上敢用」还差好几步：固定线程数、`shutdown()` 只能温和排空、任务自身抛异常没专门处理、队列无界生产者一灌就 OOM、错误码粗到只能区分「成了 / 队列停了」。这一章是 V3，把这些缺口一次性补到位。

具体覆盖三件事：

- **任务异常隔离**——一个任务在 worker 里 `throw` 了，绝不能让 worker 跟着挂掉。
- **`shutdownNow()`**——除了温和排空，再加一种「立即停、扔掉队里没轮到的」的关法。
- **有界队列 + 背压 + 错误分类**——给队列加容量上限，满了时区分「阻塞等」和「立刻拒绝」，错误码升级成 `enum class`，提交失败拆成专门的异常类型。

中间插一节专门讲清楚「异常是怎么从 worker 跨线程跑到 `future` 那一头的」——这条链路是理解 V3 几个设计选择的钥匙。

## 1. 任务异常隔离：不让一个任务带走 worker

最先想清楚的问题：一个 `submit` 进来的任务在 worker 里 `throw` 了，会发生什么？这是面试高频题，也是真实事故来源。

如果异常逃出 `workerLoop`，`std::thread` 的函数体没接住未捕获异常，运行时直接调 `std::terminate` 把进程干掉；就算侥幸不挂，少一个 worker，池子线程数悄悄变少，灌满任务后剩下的全卡死。所以「worker 不能因为任务异常而退出」是个硬底线。

但**现状其实没那么糟**——这一点必须先说清楚，避免重复发明轮子。V2 起 `submit` 走的是 `packaged_task` 路径：

```cpp
auto pt = std::make_shared<std::packaged_task<R()>>(std::move(task));
queue_.push([pt] { (*pt)(); });
return pt->get_future();
```

`std::packaged_task::operator()` 内部已经替我们写好了「`try` 你的 callable，`catch(...)` 把异常存进关联的 promise」的逻辑。所以你的任务即使 `throw`，异常也**到不了** `workerLoop`，会被 `packaged_task` 在 `(*pt)()` 这一层吃掉，转手扔给 future——调用方 `future.get()` 时把它重抛出来。下一节会把这条链路完整拆一遍。

那 V3 还要改什么？补两个真正的缺口：

1. **`workerLoop` 自己也要 `try/catch(...)` 兜底**。当前 `packaged_task` 帮我们吃异常，但将来如果加一个 fire-and-forget 的 `post()`（不返回 future、不走 `packaged_task`），worker 就是异常的唯一出口；提前把兜底写好，新接口加进来时不用回头改 `workerLoop`。
2. **可选的异常钩子 `setExceptionHandler`**——把 worker 兜底接到的异常交给用户决定怎么处理（打日志、上报监控等等）。

实现就这几行：

```cpp
class ThreadPool {
public:
    using ExceptionHandler = std::function<void(std::exception_ptr)>;

    void setExceptionHandler(ExceptionHandler handler) {
        exceptionHandler_ = std::move(handler);
    }

private:
    void workerLoop();
    ExceptionHandler exceptionHandler_;   // 默认值在构造函数初始化列表里装
};

inline void ThreadPool::workerLoop() {
    std::function<void()> task;
    while (taskQueue_.pop(task) == QueueStatus::OK) {
        try {
            task();
        } catch (...) {
            // worker 必须活下来，无论 task 还是 handler 抛什么
            try {
                if (exceptionHandler_) {
                    exceptionHandler_(std::current_exception());
                }
            } catch (...) {
                // 钩子自己抛也吞掉
            }
        }
    }
}
```

两层 `try/catch` 看着冗余其实必要：内层兜的是「用户装的钩子自己抛异常」——不挡的话钩子里的异常会逃到外层 `catch(...)` 之外，再次让 worker 死。安全网要一直铺到 worker 退栈为止。

构造时还有一个易错点：**默认钩子的赋值必须在 worker 启动之前完成**。如果写成：

```cpp
ThreadPool::ThreadPool(...) {
    for (...) workers_.emplace_back(&ThreadPool::workerLoop, this);
    exceptionHandler_ = [](...) { ... };   // ← 太晚了
}
```

worker 线程已经在跑、可能正在读 `exceptionHandler_`，构造线程同时在写——`std::function` 不是原子的，数据竞争。把默认钩子放进**构造函数初始化列表**，保证 worker spawn 之前已经装好：

```cpp
ThreadPool::ThreadPool(int n, size_t cap)
    : taskQueue_(cap)
    , exceptionHandler_([](std::exception_ptr ex) {
        try { if (ex) std::rethrow_exception(ex); }
        catch (const std::exception& e) { std::cerr << "[pool] " << e.what() << "\n"; }
        catch (...)                     { std::cerr << "[pool] unknown exception\n"; }
    }) {
    workers_.reserve(n);
    for (int i = 0; i < n; i++) workers_.emplace_back(&ThreadPool::workerLoop, this);
}
```

## 2. 异常是怎么跨线程跑到 future 那一头的

上一节反复提到「`packaged_task` 把异常吃掉、塞进 future、调用方 `get()` 时重抛」——这条链路具体怎么工作？这一节把它拆开。理解它，下面所有「钩子何时触发」「`broken_promise` 怎么来的」「将来想让钩子覆盖所有任务该怎么改」之类的问题就都通了。

整条路径如下：

```
你的 lambda 抛出
      │ throw
      ▼
packaged_task::operator()    ← worker 线程在这一层 catch
      │ promise.set_exception(std::current_exception())
      ▼
shared state                 ← future 和 packaged_task 内部 promise 共享的一块对象
   {  ready: true,
      result: <empty>,
      exception_ptr: ●─────┐
   }                       │ 同一个堆上的异常对象
                           │
主线程 future.get()        │
      │ 检查 state.exception_ptr 非空
      │ std::rethrow_exception(eptr)
      ▼
主线程 catch (const std::runtime_error&)
```

四段分别看。

### 2.1 `packaged_task::operator()` 的内部 catch

`std::packaged_task<R()>` 持有两样东西：你的 callable + 一个内部的 `std::promise<R>`。它的 `operator()` 大致等价于：

```cpp
void operator()() {
    try {
        if constexpr (std::is_void_v<R>) {
            callable_();
            promise_.set_value();
        } else {
            promise_.set_value(callable_());
        }
    } catch (...) {
        promise_.set_exception(std::current_exception());
    }
}
```

注意这个 `catch(...)`——这就是为什么任务异常**到不了** `workerLoop` 的外层 `try/catch`。`packaged_task` 把异常**改了一条路径**：不再向 worker 线程的调用栈上传，而是横着塞进 shared state。

### 2.2 `std::current_exception()` 和 `exception_ptr`

正常 C++ 异常是栈上的临时对象，离开 catch 块就析构了。但 V3 这里要把它**跨线程**送给 future 持有者，对象必须能活得比 catch 块更久。

`std::current_exception()` 在 catch 块里调用，返回一个 `std::exception_ptr`：

- 把当前正在处理的异常对象**复制（或共享引用）到堆上**
- `exception_ptr` 是引用计数智能指针，类似 `shared_ptr<异常对象>`
- 类型擦除：不管你抛的是 `int` / `std::runtime_error` / 自定义类，都能装

`promise.set_exception(eptr)` 把这个 `exception_ptr` 存进 shared state，引用计数 +1。此后哪怕 worker 线程跑完、`packaged_task::operator()` 退栈，堆上那个异常对象还活着。

### 2.3 shared state：future 和 promise 的中间人

`std::future` 和 `std::promise` 内部都指向同一个**共享状态对象**（标准库内部实现，对用户不可见），结构大致是：

```cpp
struct SharedState {
    std::variant<std::monostate, T, std::exception_ptr> result;
    std::atomic<bool> ready;
    std::mutex mtx;
    std::condition_variable cv;
};
```

- `promise.set_value(x)` → `result` 放 T，ready=true，notify
- `promise.set_exception(eptr)` → `result` 放 `exception_ptr`，ready=true，notify
- `future.get()` → 等 ready，然后看 result 装的是 T 还是 exception_ptr

`packaged_task` 自带一个内部 promise，`get_future()` 给调用方的就是这个 promise 关联的 future——所以 task 那边 `set_exception` 写进 state，调用方这边 `get` 立刻能读到。

### 2.4 `future.get()` 的重抛

伪代码：

```cpp
T future::get() {
    wait();                                           // 等 ready
    if (state_->result holds exception_ptr) {
        std::rethrow_exception(state_->get_eptr());   // 在 get() 调用方线程里重抛
    }
    return std::move(state_->get_value());
}
```

关键是 `std::rethrow_exception(eptr)`：用 `eptr` 持有的那个堆上异常对象，**在当前线程**重新走一遍 C++ 抛异常的流程。流程一样意味着：

- `catch (const std::runtime_error& e)` 用的是 C++ 标准的类型匹配，能精确接住
- `e.what()` 拿到的是原始异常对象的内容，没有损失
- 多态正常工作（catch 写宽点也能接住）
- catch 链匹配完，堆上异常对象的引用计数归零、析构

也就是说，**抛异常的线程和 catch 异常的线程不是同一个**，但语义看起来就像同线程一样自然。这是 `future` 的核心价值之一——除了搬运返回值，它也搬运异常。

### 2.5 回到「钩子为什么不触发」

把整条链对完，上一节那句「钩子对 `submit` 的任务不会触发」就特别清楚了：异常在 `packaged_task::operator()` 的 catch 里就被截胡，**根本到不了** `workerLoop` 的外层 `try/catch`。钩子是挂在外层 catch 里的——异常没进 catch，钩子当然不调。

那钩子还有什么用？两种场景：

- **wrapper lambda 自己抛**（理论上不会发生，纯防御）。比如 `pt` 空解引用、`std::bad_function_call` 之类，异常没经过 `packaged_task` 的内层 catch，会直接逃到外层。
- **将来的 `post()`**——不返回 future、不走 `packaged_task`，worker 是异常的唯一出口，钩子就成了刚需。

如果想让钩子对所有 `submit` 任务都触发，得把 `packaged_task` 换成手动 `std::promise + try/catch`，模板就是 2.1 那段伪代码：在 catch 块里**先 `set_exception` 通知 future，再调钩子**。这是另一个设计取舍，V3 不做。

## 3. `shutdownNow()`：立即停、丢弃未执行任务

V2 的 `shutdown()` 是「温和排空」——队列里已有的任务全跑完才退。但有时候你就是想「尽快停」：正在执行的那几个让它跑完，队列里还没轮到的直接丢。这就是 `shutdownNow()`。

实现拆两步。

**第一步**，给 `BlockingQueue` 加一个「清空 + 停」绑成原子的操作：

```cpp
template <typename T>
void BlockingQueue<T>::stopAndClear() {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        std::queue<T>{}.swap(queue_);   // 等价于 clear，O(1) 释放
        stopped_ = true;
    }
    notEmpty_.notify_all();
    notFull_.notify_all();
}
```

为什么不另开一个独立的 `clear()`？因为「清空但仍接收新任务」对线程池没用——会出现「我刚清完你又塞进来一个」的诡异竞争。清空和停止必须是同一步原子操作。

**第二步**，给 `ThreadPool` 加 `shutdownNow()`，跟 `shutdown()` 复用同一个 `stopped_` 拦截：

```cpp
void ThreadPool::shutdown() {
    if (!stopped_.exchange(true)) {
        taskQueue_.stop();                  // 温和：让队里的任务跑完
        for (auto& w : workers_) if (w.joinable()) w.join();
    }
}

void ThreadPool::shutdownNow() {
    if (!stopped_.exchange(true)) {
        taskQueue_.stopAndClear();          // 立即：清队 + 停
        for (auto& w : workers_) if (w.joinable()) w.join();
    }
}
```

`stopped_.exchange(true)` 是个原子操作，谁先调到谁就拿到 `false` 这个返回值，进真正的收尾分支；后到的都拿 `true`，直接 return。这天然就是「**先到先定，后到 no-op**」：

| 调用顺序 | 行为 |
|---|---|
| `shutdown()` → `shutdownNow()` | 第一次走温和排空，第二次直接返回（已经在排空了，强行升级语义只会让排空中的任务一半被丢，乱） |
| `shutdownNow()` → `shutdown()` | 第一次走立即清空，第二次直接返回（已经丢完了，再调 shutdown 没意义） |
| `shutdown()` × 2 / `shutdownNow()` × 2 | 同 V2 的幂等保证 |

被丢弃任务对应的 `future` 会怎样？这正是上一节那条异常链路的一个有趣分支：lambda 里捕获的 `shared_ptr<packaged_task>` 因为 `stopAndClear` 被释放，最后一份引用归零，`packaged_task` 析构——它**从未被调用过**，所以内部的 `promise` 既没 `set_value` 也没 `set_exception` 就跟着析构了。

标准库对这种情况有专门规定：promise 在没 set 任何值的状态下析构，关联的 future 进入 "broken" 状态，`get()` 会抛 `std::future_error`，错误码是 `std::future_errc::broken_promise`。这是**预期行为**，不是 bug——「我让你立即停，你就别指望那些没跑的任务还有结果」。调用方代码长这样：

```cpp
try {
    auto result = future.get();
} catch (const std::future_error& e) {
    if (e.code() == std::future_errc::broken_promise) {
        // 这个任务被 shutdownNow 丢了
    }
}
```

## 4. 有界队列、背压、错误分类

V2 的 `BlockingQueue` 是无界的——生产者疯狂 `submit` 而 worker 跟不上，队列内存无限涨，最后 OOM。工程上要给队列一个容量上限，满了时得有策略。

策略不是单一的，V3 同时暴露两种：

- **阻塞 `push`**：满了就等到有空位（或者队列被停了）。这把背压传给调用方——你提交得快，那就让你等。
- **`tryPush`**：满了立即返回 `FULL`。调用方决定重试、丢弃，还是降级到本地执行。

对应到 `ThreadPool` 就是 `submit`（阻塞）和 `trySubmit`（非阻塞）两个接口。

### 4.1 错误码升级成 `enum class`

老版本 `BlockingQueue` 的错误用 `#define ERROR_QUEUE_STOPPED 1`，函数返回 `int`。三态了之后这套就不够用，升级成 `enum class`：

```cpp
enum class QueueStatus : int {
    OK      = 0,
    STOPPED = 1,
    FULL    = 2,
};
```

`enum class` 比 `#define` 好在两点：有命名空间不污染、类型安全（不能跟普通 int 隐式转换）。

`ThreadPool` 这一层把 `QueueStatus` 翻译成异常族——调用方写 `try/catch` 比写 `if (status == ...)` 顺手得多，而且能精确分类：

```cpp
class ThreadPoolError : public std::runtime_error {
    using std::runtime_error::runtime_error;
};
class ThreadPoolStopped : public ThreadPoolError {
public:
    ThreadPoolStopped() : ThreadPoolError("ThreadPool has been shutdown ...") {}
};
class ThreadPoolFull : public ThreadPoolError {
public:
    ThreadPoolFull() : ThreadPoolError("ThreadPool task queue is full.") {}
};
```

继承结构让调用方既可以精确接（`catch (const ThreadPoolFull&)`），也可以宽接（`catch (const ThreadPoolError&)` 或 `catch (const std::exception&)`），各取所需。

### 4.2 队列的双 CV 模型

无界版本只有一个 `notEmpty_` 条件变量给 `pop` 用。有界版本要再加一个 `notFull_` 给阻塞 `push` 用：

```cpp
template <typename T>
class BlockingQueue {
public:
    explicit BlockingQueue(std::size_t capacity = 0) : capacity_(capacity) {}

    QueueStatus push(T item);          // 阻塞版
    QueueStatus tryPush(T item);       // 非阻塞
    QueueStatus pop(T& item);

    void stop();
    void stopAndClear();

private:
    std::queue<T> queue_;
    std::mutex mutex_;
    std::condition_variable notEmpty_;
    std::condition_variable notFull_;
    std::size_t capacity_;             // 0 表示无界
    bool stopped_ = false;
};
```

`capacity == 0` 退化成 V2 的无界行为，这样老代码迁过来不用改默认值。

阻塞 push 的实现：

```cpp
template <typename T>
QueueStatus BlockingQueue<T>::push(T item) {
    {
        std::unique_lock<std::mutex> lock(mutex_);
        notFull_.wait(lock, [this] {
            return stopped_ || capacity_ == 0 || queue_.size() < capacity_;
        });
        if (stopped_) return QueueStatus::STOPPED;
        queue_.push(std::move(item));
    }
    notEmpty_.notify_one();
    return QueueStatus::OK;
}
```

predicate 三个条件——`stopped_ || 无界 || 有空位`——少一个就出问题：

- 不带 `stopped_`：队列停掉但还满的时候，push 永远卡死。
- 不带 `capacity_ == 0`：无界模式下永远不入队（无界时 `size() < capacity_` 永假，因为 `capacity_` 是 0）。
- 不带 `queue_.size() < capacity_`：直接没有有界判断。

`pop` 跟 V2 差别不大，但要在出队后多一步 `notFull_.notify_one()`，给可能在等空位的 push 让位：

```cpp
template <typename T>
QueueStatus BlockingQueue<T>::pop(T& item) {
    std::unique_lock<std::mutex> lock(mutex_);
    notEmpty_.wait(lock, [this] { return !queue_.empty() || stopped_; });
    if (queue_.empty()) return QueueStatus::STOPPED;
    item = std::move(queue_.front());
    queue_.pop();
    lock.unlock();
    notFull_.notify_one();   // 背压能传递的关键
    return QueueStatus::OK;
}
```

### 4.3 一个特别容易踩的坑

`stop()` 必须**两个 CV 都 `notify_all`**——否则关闭时阻塞在 `notFull_` 上等空位的 push 会永远卡死，整个程序死锁：

```cpp
void BlockingQueue<T>::stop() {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        stopped_ = true;
    }
    notEmpty_.notify_all();
    notFull_.notify_all();   // 漏了这行就会死锁
}
```

这跟 05 章 `pop` 那个 `wait(lock, [&]{ return !empty || stopped; })` 是同一个套路，只是方向反过来。**任何阻塞等待，都必须考虑被关闭信号唤醒的路径**——这是个能反复套用的模式。

### 4.4 `submit` / `trySubmit` 的封装

`ThreadPool` 这层把 `QueueStatus` 翻译成异常：

```cpp
template <typename Func>
auto ThreadPool::submit(Func task) -> std::future<std::invoke_result_t<Func>> {
    using R = std::invoke_result_t<Func>;
    auto pt = std::make_shared<std::packaged_task<R()>>(std::move(task));
    auto future = pt->get_future();
    QueueStatus s = taskQueue_.push([pt] { (*pt)(); });
    if (s == QueueStatus::STOPPED) throw ThreadPoolStopped();
    if (s != QueueStatus::OK)      throw ThreadPoolError("submit: unexpected queue status");
    return future;
}

template <typename Func>
auto ThreadPool::trySubmit(Func task) -> std::future<std::invoke_result_t<Func>> {
    using R = std::invoke_result_t<Func>;
    auto pt = std::make_shared<std::packaged_task<R()>>(std::move(task));
    auto future = pt->get_future();
    QueueStatus s = taskQueue_.tryPush([pt] { (*pt)(); });
    if (s == QueueStatus::STOPPED) throw ThreadPoolStopped();
    if (s == QueueStatus::FULL)    throw ThreadPoolFull();
    return future;
}
```

调用方使用差异：

```cpp
ThreadPool pool(4);              // 默认容量 1024
ThreadPool small(4, 8);          // 小容量，强背压
ThreadPool unbounded(4, 0);      // 显式无界（与 V2 等价）

try {
    auto f = pool.trySubmit([] { return 1; });
} catch (const ThreadPoolFull&) {
    // 满了，可以重试 / 丢弃 / 降级到本地执行
} catch (const ThreadPoolStopped&) {
    // 池子关了，没活路
}
```

`submit` 的阻塞行为有副作用：主线程灌任务时如果队列满，主线程自己就会被卡住。这正是背压的意义（强迫生产者放慢），但也意味着**`submit` 可能阻塞任意时长，不要在持锁状态下调它**。

## 5. 已敲定的决策

这一章一路上拍板的决策汇总：

| # | 决策 | 结论 |
|---|------|------|
| 1 | 异常隔离要不要加钩子 | **加**。`workerLoop` 兜底 `try/catch(...)` + 可选 `setExceptionHandler` 钩子。诚实交代：`packaged_task` 路径的异常进 future，不会触发钩子；钩子是为将来的 `post()` / 防御性兜底准备的。 |
| 2 | `shutdown` / `shutdownNow` 互斥语义 | **先到先定，后到 no-op**。靠 `stopped_.exchange(true)` 单点拦截。 |
| 3 | 有界队列容量传法 | 构造参数 `ThreadPool(int numThreads, size_t queueCapacity = kDefaultQueueCapacity)`；`kDefaultQueueCapacity = 1024`；保留 `0 = 无界` 兼容 V2。 |
| 4 | `push` 满时策略 | **两个都暴露**：`submit` 走阻塞 `push`（背压传到调用方），`trySubmit` 走 `tryPush`（满了立即抛 `ThreadPoolFull`）。 |
| 5 | 错误码 / 异常分类 | `BlockingQueue` 用 `enum class QueueStatus { OK, STOPPED, FULL }` 替换老 `#define`；`ThreadPool` 提供异常族 `ThreadPoolError` ← `ThreadPoolStopped` / `ThreadPoolFull`。 |
| 6 | 是否拆 09 | 不拆。块 1-3 全塞进本章；动态线程数 / worker 命名 / 运行时指标 / 带参 `submit` 这些「锦上添花」留给 09。 |

## 6. 测试都验证了什么

`src/test.cpp` 里 V3 测试分三层。每层用一个简易的 `v3_expect(cond, name)` 计数 + `Watchdog` 超时兜底（避免某个 case 死锁卡住整个测试套）。

**Feasibility（F1–F8）—— 语义正确性**：

- **F1** 异常隔离基本面：5 个任务其中 3 个 throw，断言抛异常的 future 能重抛同一异常、正常任务 future 返回正确值、worker 没死。
- **F2** 钩子在 submit 路径**不**触发：反向回归测试，验证文档对钩子触发时机的描述跟实现一致。如果未来 submit 重构走 promise + try/catch，此测试会变红，提醒同步更新文档。
- **F3** `shutdown` 后 `submit` 抛 `ThreadPoolStopped`：精确类型 catch 验证异常分类生效。
- **F4** `shutdownNow` 丢弃未执行任务：断言被丢任务的 `future.get()` 抛 `broken_promise`、`executed < submitted`。
- **F5** `shutdown` / `shutdownNow` 互斥幂等：4 种顺序（同 × 2 + 互换 × 2）各跑一次，都不抛、不死锁。
- **F6** `trySubmit` 满队列抛 `ThreadPoolFull`：占住 worker → 填满队列 → 第 N+1 次 `trySubmit` 应抛。
- **F7** `submit` 满队列阻塞（背压）：测量 6 次 `submit` 的耗时，前 3 次毫秒级、后 3 次出现 ~100ms 的阻塞。
- **F8** 关闭时唤醒阻塞的 push：生产者卡在满队列上，调 `shutdown()` 后必须能被唤醒抛 `ThreadPoolStopped` 退出——验证 4.3 那个坑没踩到。

**Stability（S1, S2）—— 高并发不丢不卡**：

- **S1** 4 个生产者 × 50000 任务 + 中途 `shutdown`：断言 `sum(accepted) == executed`（已接收的全跑了）、`accepted + rejected == 200000`（所有 submit 都有明确结果）。
- **S2** 同上换 `shutdownNow`：断言 `executed < accepted`（有任务被丢）。

**Performance（P1）—— 背压效果对比**：

- 200000 个极轻任务，三档容量（0 / 1024 / 16）。打印总耗时 + 单次 `submit` 的 P50 / P99 延迟。容量越小 P99 越高——这就是背压把生产者节流的可观测信号。

跑下来都通过，关键的「不丢任务 / 不死锁 / 背压可观测」三件事都站住了。

## 7. 小结

V3 收尾后，线程池补完了「工程可用」的最后几块拼图：

- worker 在任务异常面前不会死，钩子接口为未来的 `post()` 留好了出口
- `shutdown()` / `shutdownNow()` 给调用方两种关法的语义，互斥幂等
- 队列有了容量上限和背压，错误码升级成 `enum class`，异常族让 `submit` 失败的原因清晰分类

理解整章的关键是中间那条**异常跨线程链路**：知道 `packaged_task → promise → shared state → future.get` 是怎么把异常从 worker 搬到调用方的，钩子为什么不触发、`shutdownNow` 后的 future 为什么抛 `broken_promise`、未来想让钩子覆盖所有任务该怎么改——这些都从同一棵知识树上长出来。
