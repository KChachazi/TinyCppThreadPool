# 任务抽象与结果返回

线程系列写到这里，前三篇解决的其实是同一类问题：怎么让多个线程安全地共用数据。
- 01 篇讲 线程怎么创建、怎么收尾。
- 02 篇讲 多个线程同时改一份数据为什么会出错、怎么用锁修好。
- 03 篇讲 多把锁怎么避免死锁。

但这些都还停留在线程能正确地跑完。本篇将要从另一个角度上出发，解决一个问题——线程跑完之后，它算出来的那个结果，怎么交回到你手上？

这个问题是从「线程」走向「线程池」的关键一步。因为，线程池的本质不是「能起很多线程」，而是「提交一个任务，稍后能取回其结果」。

## 0. 问题：结果留在线程里

先看 `std::thread` 怎么对待返回值。给它一个有返回值的函数：

```cpp
int compute() { return 42; }

int main() {
    std::thread t(compute);   // 返回的 42 去哪了？
    t.join();
}
```

这段代码能编译、能运行，但 `compute()` 返回的 `42` 直接被丢掉了。`std::thread` 的职责只有一个——把这个函数在新线程里跑起来；它根本不关心函数返回什么。

现在，我们要想办法把结果拿出来，传统方法是在外面开一个变量，让线程把结果写进去：

```cpp
int result = 0;
std::thread t([&result]() { result = compute(); });
t.join();
std::cout << result << "\n";   // 42
```

能用，但很不舒服。我们要取出一个变量就必须做到：
- 提前在外面先准备好一个变量，还要保证它的生命周期盖过整个线程。
- `result` 只有 `join()` 之后才有效。在那之前读它就是数据竞争。这里靠 `join()` 兜底，可一旦任务变多、逻辑变绕，就很容易读早了。
- 无从判断 `result` 是否已经运算完成。
- 任务一多，代码里就堆满了共享变量和 `join()`。

其实，最根本的问题在于，`std::thread` 只管「执行」，不管「结果」，于是结果只能靠你用共享变量手动搬运。

为此，C++ 专门提供了一组工具——`std::future`，`std::async`，`std::packaged_task`，`std::promise`。

## 1. std::future

`std::future<T>` 代表一个「现在还没有、将来会有」的 `T` 类型结果。你拿着这个 future，不用知道结果是谁算的，在哪个线程算的，只要在需要时向它要即可。

`std::future<T>`的主要接口有：

| 成员函数 | 作用 |
|----------|------|
| `get()` | 取结果。结果没就绪就阻塞等待，就绪了立刻返回 |
| `wait()` | 只等待结果就绪，不取值 |
| `wait_for()` | 最多等一段时间，返回当前状态 |
| `valid()` | 这个 future 是否还关联着一个结果 |

其中 `get()` **只能调用一次**，其语义是「把结果取走」，取走之后 future 就空了（`valid()` 变成 `false`），再调 `get()` 是未定义行为。如果结果是只能移动、不能拷贝的类型（比如 `std::unique_ptr`），这个「取走」的语义就更顺理成章了。

如果同一个结果需要被多个线程各自读取，可以使用 `std::shared_future<T>`。它能被拷贝，多个副本共享同一份结果，`get()` 也能反复调用。并且每次返回的是对结果的引用，而不是把它搬走。拿到 `shared_future` 的常见办法是对一个 `future` 调用 `share()`，转换之后原 `future` 失效。

机制上，`future` 和 `shared_future` 指向的是同一个「共享状态」，区别只在于 `future` 独占这个状态、`get()` 把结果移走；`shared_future` 允许多方共享、`get()` 只是读取。它的典型用途是把一个结果广播给多个等待者，比如多个线程都要等同一个「资源已就绪」的信号。

future 不会凭空出现，它总是和一个「结果的生产者」成对存在：一端是 future，消费者拿着它等结果；另一端是生产者，负责把结果填进去。C++ 提供了三种生产者，也就是三种制造 future 的方式。

## 2. 三种制造 future 的方式

### 2.1 std::async：直接把任务跑起来

最省事的一种。把一个可调用对象交给 `std::async`，它负责安排执行，并立刻返回一个 future：

```cpp
#include <future>
#include <iostream>

int add(int a, int b) { return a + b; }

int main() {
    std::future<int> result = std::async(std::launch::async, add, 3, 4);
    // main 在这里可以继续做别的事，add 在另一个线程里跑
    std::cout << result.get() << "\n";   // 需要结果时再 get，输出 7
}
```

第一个参数是启动策略，有如下两种：

| 启动策略 | 含义 |
|----------|------|
| `std::launch::async` | 立刻在新线程里执行 |
| `std::launch::deferred` | 推迟执行，直到 `get()` / `wait()` 时才在调用线程里跑 |
| 不写 | 由实现决定，可能 async 可能 deferred，不可预测 |

不写策略时行为是不确定的——有可能根本没开新线程，任务一直拖到 `get()` 才执行。所以**建议总是显式写 `std::launch::async`**。

此外，`std::async` 还有一个坑，导致主线程阻塞。具体来看这一行代码：

```cpp
std::async(std::launch::async, slow_task);   // 这一行会阻塞！
```

`launch::async` 产生的 future 在析构时会等待任务跑完。上面这行没把 future 接进变量，那个临时 future 当场就析构了，于是这一行会一直卡到 `slow_task` 结束。

结果就是写着是异步，实际跑起来是同步。想要 fire-and-forget，就必须把 future 接住，并让它活得够久。

### 2.2 std::packaged_task：把任务打包，稍后再跑

`std::async` 是「提交即执行」，但线程池需要的不是这个。线程池的任务是，先把任务收下并放进队列，之后再由某个工作线程取出来跑。也就是说，「打包任务」和「执行任务」得拆成两步。

`std::packaged_task<Sig>` 正是为此而生。它把一个可调用对象包起来，内部关联一个 future。此时我们可以先用 `get_future()` 把结果通道取走，任务对象本身可以存储、移动、传给别的线程，等它真正被调用时，函数的返回值会自动写进那个 future。

如下是一个代码示例：

```cpp
#include <future>
#include <iostream>
#include <thread>

int work(int x) { return x * x; }

int main() {
    std::packaged_task<int(int)> task(work);        // 打包
    std::future<int> result = task.get_future();    // 先取出结果通道

    std::thread t(std::move(task), 5);              // 任务在别处、稍后执行
    t.join();

    std::cout << result.get() << "\n";              // 25
}
```

注意，上面的代码里使用了 `std::move(task)`，这是因为 `packaged_task` 只能移动、不能拷贝，一个任务的执行权只该有一份。正是「可移动、可存储、自带结果通道」这三点，让它成为线程池任务的标准载体。后续我们会用它搭建起一个任务队列。

### 2.3 std::promise：结果由你手动写入

`async` 和 `packaged_task`，结果都来自一个函数的返回值，而 `promise` 的结果可以来自一个由我们决定的时刻，无论是一个事件还是一次回调。

`promise` 是 future 的另一端：生产者侧拿着 promise，在某个时刻调用 `set_value()` 把结果填进去；消费者侧拿着对应的 future 等这个值。

```cpp
#include <iostream>
#include <thread>
#include <future>
#include <chrono>

int main() {
    std::promise<int> prom;
    std::future<int> result = prom.get_future();

    std::thread worker([&prom]() {
        std::this_thread::sleep_for(std::chrono::seconds(2));
        prom.set_value(42);            // 由你决定「此刻结果有了」
    });

    std::cout << "等待结果...\n";
    std::cout << "结果：" << result.get() << "\n";   // 阻塞到 set_value 被调用
    worker.join();
}
```

需要注意：
- `get_future()` 只能调一次，重复调用会抛 `std::future_error`。习惯上先拿 future，再把 promise 交给线程。
- 例子里用 `[&prom]` 按引用捕获，worker 操作的就是 `main` 里那个 promise。用引用捕获就必须保证 promise 的生命周期盖过线程的整个运行期。
- `promise` 和 `packaged_task` 的分工很清楚：`packaged_task` 的结果是「函数算出来的」，`promise` 的结果是「你亲手塞进去的」。

三者放在一起对比：
| 工具 | 结果来自 | 由谁执行 | 典型场景 |
|------|---------|---------|---------|
| `std::async` | 函数返回值 | 库自己安排 | 一次性异步调用 |
| `std::packaged_task` | 函数返回值 | 你决定何时、在哪 | 任务队列、线程池 |
| `std::promise` | 手动 `set_value` | —— | 结果来自事件或回调 |

## 3. future 的两个进阶能力：等超时、接异常

前面 `get()` 都是「一直等到结果就绪」。future 还有两个常被用到的能力。

### 3.1 wait_for：不想无限等下去

`get()` 会一直阻塞到结果就绪。但有时你不愿意无限等——等够一定时间就该走别的路。`wait_for()` 等一个指定时长，然后返回一个 `future_status` 告诉你现在什么情况：

```cpp
#include <iostream>
#include <future>
#include <chrono>

int slowTask() {
    std::this_thread::sleep_for(std::chrono::seconds(2));
    return 42;
}

int main() {
    std::future<int> result = std::async(std::launch::async, slowTask);

    auto status = result.wait_for(std::chrono::seconds(3));
    if (status == std::future_status::ready) {
        std::cout << "结果：" << result.get() << "\n";
    } else {
        std::cout << "超时，改用兜底方案\n";
    }
}
```

`future_status` 有三种取值：`ready`（结果就绪）、`timeout`（等够了还没好）、`deferred`。

注意两点：
- `wait_for()` 超时**不会取消任务**。
- 它可以反复调用，每次重新等一段，直到你决定放弃。

如果把上面的等待时长改成 `milliseconds(500)`，任务还没跑完就会超时，走 else 分支。

### 3.2 异常会跟着 future 一起回来

异常本身不能跨线程传播。一个线程内部的异常无法直接被另一个线程的 `try/catch` 捕获；如果线程函数抛出的异常没有被线程自身捕获，程序将调用 `std::terminate`。

但 future 把这件事接管了。任务执行中如果抛了异常，运行时会捕获它、转成 `std::exception_ptr`，存进 future 的共享状态。等你调 `get()` 时，它不会返回值，而是把那个异常**重新抛出来**：

```cpp
#include <iostream>
#include <future>
#include <stdexcept>

int risky_task() {
    throw std::runtime_error("Task failed!");
    return 0;
}

int main() {
    std::future<int> result = std::async(std::launch::async, risky_task);
    try {
        int value = result.get();        // 异常在这里被重新抛出
        std::cout << "结果：" << value << "\n";
    } catch (const std::exception& e) {
        std::cout << "捕获到异常：" << e.what() << "\n";
    }
}
```

异常就这样「跨过」了线程边界——任务在哪个线程里抛的不重要，调用方只要在 `get()` 外面套一层 `try/catch` 就能统一处理失败。`async` 和 `packaged_task` 都自动带这个行为；用 `promise` 的话，则要你手动调 `prom.set_exception(std::current_exception())` 把异常送进去。

对线程池来说这个机制很省事：提交任务的人不必关心任务在哪个线程跑、会不会出错，错误会顺着 future 自己回来。

## 4. 工程实例：最小任务队列

把这一篇的东西拼起来，做一个最小的任务队列。它已经是线程池的雏形了。

### 4.1 需求

- 主线程不断往队列里提交任务。
- 一个工作线程不停地从队列里取任务、执行。
- 提交方拿到一个 future，能等到任务完成。
- 能干净地关闭：通知关闭后，工作线程把剩下的任务做完再退出，不丢任务、不卡死。

### 4.2 设计

- **任务存储**：用 `std::packaged_task<void()>` 装进 `std::queue`。选 `packaged_task` 是因为要「先收下、后执行」，正好是 2.2 节说的场景。
- **队列共享**：队列被提交线程和工作线程同时读写，要用 `mutex` 保护。
- **工作线程等待**：队列空的时候，工作线程不能忙等待。用 `std::condition_variable` 让它顺面，有任务时再被唤醒——条件变量的细节是下一篇阻塞队列的主题，这里只要知道它干的是「没任务就睡，有任务就醒」这件事。
- **关闭**：一个 `shutdown` 标志。工作线程的退出条件是「已关闭，且队列已空」——这样关闭后剩余任务还能被做完。

### 4.3 实现

```cpp
class TaskQueue {
public:
    std::future<void> submit(std::function<void()> task) {
        std::packaged_task<void()> packagedTask(task);
        std::future<void> future = packagedTask.get_future();
        {
            std::lock_guard<std::mutex> lock(mtx);
            if (shutdown) {
                throw std::runtime_error("submit on stopped TaskQueue");
            }
            tasks.push(std::move(packagedTask));
        }
        cv.notify_one();
        return future;
    }

    void work() {
        while (true) {
            std::packaged_task<void()> task;
            {
                std::unique_lock<std::mutex> lock(mtx);
                cv.wait(lock, [this] { return !tasks.empty() || shutdown; });
                if (shutdown && tasks.empty()) {
                    return;
                }
                task = std::move(tasks.front());
                tasks.pop();
            }
            task();
        }
    }

    void stop() {
        {
            std::lock_guard<std::mutex> lock(mtx);
            shutdown = true;
        }
        cv.notify_all();
    }

private:
    std::queue<std::packaged_task<void()>> tasks;
    std::mutex mtx;
    std::condition_variable cv;
    bool shutdown = false;
};
```

三个方法各管一段：
- `submit()`：把传进来的可调用对象包成 `packaged_task`，**先**取出 future，**再**在锁的保护下把任务推进队列，然后唤醒一个工作线程。future 是在加锁之前就取好的，任务一旦进了队列，随时可能被工作线程取走执行，那时再去碰这个 task 对象就晚了。
- `work()`：工作线程的主循环。`cv.wait` 的谓词 `!tasks.empty() || shutdown` 同时等待有新任务，或者要关闭，任一成立就被唤醒。醒来后如果是「已关闭且队列空」，就退出；否则取一个任务出来。注意 `task()` 是在解锁之后才执行的——执行任务不该占着队列的锁。
- `stop()`：在锁保护下把 `shutdown` 置位，再 `notify_all` 把所有等待中的工作线程都叫醒，让它们重新检查退出条件。

驱动代码：
```cpp
int main() {
    TaskQueue taskqueue;
    std::thread worker(&TaskQueue::work, &taskqueue);

    auto future1 = taskqueue.submit([]() {
        std::this_thread::sleep_for(std::chrono::seconds(1));
        std::cout << "Task 1 completed" << std::endl;
    });
    auto future2 = taskqueue.submit([]() {
        std::this_thread::sleep_for(std::chrono::seconds(2));
        std::cout << "Task 2 completed" << std::endl;
    });
    auto future3 = taskqueue.submit([]() {
        std::this_thread::sleep_for(std::chrono::seconds(3));
        std::cout << "Task 3 completed" << std::endl;
    });

    future1.get();
    future2.get();
    future3.get();

    taskqueue.stop();
    worker.join();

    std::cout << "All tasks completed" << std::endl;
}
```

提交三个任务后，`main` 用三个 `future.get()` 依次等它们完成，再 `stop()` 关闭队列、`join()` 回收工作线程。输出是：

```
Task 1 completed
Task 2 completed
Task 3 completed
All tasks completed
```

到这里，这个 `TaskQueue` 已经具备了线程池的核心骨架：任务能提交、能排队、能被工作线程取走执行、结果能通过 future 拿回、还能干净关闭。它和一个真正的线程池之间，主要差在两点——只有一个工作线程（线程池要一组），以及这个手写队列还比较粗糙（下一篇会专门做一个像样的阻塞队列）。

## 5. 小结

这一篇把「线程能跑」推进到了「任务能把结果交回来」。其中有几个关键角色：
- `std::thread` 负责执行，但它不管结果。
- `std::future` 是结果的独占句柄，`get()` 只能调用一次并把结果取走；需要多次读取时可改用 `std::shared_future`。
- 制造 future 有三种方式，分别为 `std::async`（提交即执行）、`std::packaged_task`（打包后稍后执行，线程池用的就是它）、`std::promise`（结果由你手动写入）。

把这些拼起来，就得到了 `TaskQueue`，这已经是一个线程池的雏形。

它还缺一个真正好用的队列：能安全地多线程读写、空时阻塞、关闭时唤醒。这正是下一篇「阻塞队列设计」要做的事。
