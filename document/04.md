# 04. 任务抽象与结果返回

前面几节已经把线程、锁、死锁、条件变量这些基础环节串起来了。到了这一节，问题开始变得更实际：

我不只是想把一个函数丢进线程里执行完就结束，而是希望它能把结果返回给我。

这就引出了这一节的核心：**任务抽象**。

## 1. 本节目标

如果我把工作直接交给 `std::thread`，它确实能跑，但有两个很现实的问题：

1. 线程函数本身通常没有直接的返回值通道。
2. 我很难把"任务本身"和"执行任务的线程"分开管理。

在线程池里，这个问题会更明显。线程池关心的是：

1. 有哪些任务要执行。
2. 任务执行完后，结果怎么取回来。
3. 调用者怎么知道任务已经完成。

所以这一节的目标不是"再学一个新接口"，而是先建立一种思维方式：

1. 线程负责执行。
2. 任务负责描述工作。
3. 返回值负责把结果送回调用者。

## 2. 核心概念区分

### 2.1 可调用对象

在 C++ 里，只要一个东西"能像函数一样被调用"，它就可以被看成可调用对象。

常见的有：

- 普通函数
- lambda 表达式
- 函数对象
- `std::bind` 绑定后的结果

这很重要，因为线程池后面并不关心你交进来的到底是函数还是 lambda，它只关心：**这个东西能不能被执行**。

### 2.2 任务

我更愿意把任务理解成"要做什么"，而不是"谁来做"。

比如：

- 计算平方。
- 统计文本长度。
- 处理一段数组。

这些都是任务。至于最后由哪个线程执行，那是调度层的事情。

### 2.3 返回结果

任务执行完以后，结果不能只打印在屏幕上就算结束。

在工程里更常见的是：

1. 调用方发起任务。
2. 调用方持有一个结果句柄。
3. 任务完成后，调用方再取结果。

这一节里最适合承担这个职责的，就是 `std::future`。

## 3. `std::thread` 的局限性

`std::thread` 的定位是"启动一个线程执行某段代码"。它并不是一个天然的"任务对象"。

这带来几个限制：

1. 线程启动后，结果通常只能靠共享变量传回去。
2. 如果多个任务都这么做，管理会越来越乱。
3. 调用者和执行者之间的边界不清晰。

这也是为什么线程池一般不会直接把"线程"暴露给业务代码，而是暴露"任务提交接口"。

## 4. `std::future` 是什么

`std::future` 可以理解成一个"未来会有结果的句柄"。

调用者拿到它之后，可以：

1. 等结果。
2. 取结果。
3. 判断任务是否已经完成。

它最重要的价值不是语法本身，而是把"提交任务"和"等待结果"分开了。

### 4.1 常见使用方式

```cpp
#include <future>
#include <iostream>

int add(int a, int b) {
    return a + b;
}

int main() {
    std::future<int> result = std::async(std::launch::async, add, 3, 4);
    std::cout << result.get() << std::endl;
}
```

这里最关键的是：

1. `add` 被当成任务交出去。
2. `std::future<int>` 负责接收结果。
3. `get()` 会拿到最终返回值。

### 4.2 `get()` 的特点

`future::get()` 不是普通读值，它带有"取一次结果"的语义。

这意味着：

1. 调用前如果结果还没好，它会等待。
2. 调用后结果被消费，通常不能重复取。

这和普通变量不一样，所以不能把它当成简单的 `int` 去理解。

### 4.3 `std::async` 用法速查

`std::async` 是最简洁的异步任务提交方式，不需要手动创建线程，不需要 `packaged_task`，直接返回 `future`。

**基本语法**：

```cpp
std::future<ReturnType> f = std::async(policy, callable, args...);
```

**启动策略**（policy）：

| policy | 含义 |
|---|---|
| `std::launch::async` | 立刻在新线程里执行 |
| `std::launch::deferred` | 懒执行，等到 `get()` 或 `wait()` 被调用时才在调用方线程里执行 |
| 不写 policy | 由实现决定，通常是 async 或 deferred 的混合，不可预测 |

**建议始终显式写 `launch::async`**，避免 deferred 带来的意外行为。

**一个常见的坑**：

```cpp
std::async(std::launch::async, some_task);  // 没有接收返回值
```

这行代码会在当前行阻塞，直到 `some_task` 完成。原因是 `std::async` 返回的 future 如果没有被接收，会立即析构，而 `launch::async` 的 future 析构时会等待任务完成。如果你想真正的"fire and forget"，必须接收这个 future，并确保它活得够久。

**和 `packaged_task` 的使用场景对比**：

- `std::async`：适合一次性的异步调用，不需要队列，结果直接通过 future 拿回来。简单场景首选。
- `packaged_task`：适合需要把任务放进队列、延迟执行的场景，比如线程池。任务和执行时机分离。

## 5. `std::packaged_task` 的作用

如果说 `future` 是结果句柄，那 `packaged_task` 更像是"任务包装器"。

它做的事情是：

1. 把一个可调用对象包装起来。
2. 自动帮我准备好一个与之关联的 `future`。
3. 等任务真正执行时，再把结果写进这个 `future`。

这在线程池里特别有价值，因为线程池一般需要把任务先存起来，之后再统一执行。

### 5.1 为什么它适合线程池

线程池里最常见的模式不是"线程创建后立即跑一个固定函数"，而是：

1. 提交一个任务。
2. 任务进入队列。
3. 某个工作线程取出任务并执行。
4. 提交者拿着 `future` 等结果。

`std::packaged_task` 正好把"可执行任务"和"结果返回"绑在了一起。

### 5.2 一个最小例子

```cpp
#include <future>
#include <iostream>
#include <thread>

int work(int x) {
    return x * x;
}

int main() {
    std::packaged_task<int(int)> task(work);
    std::future<int> result = task.get_future();

    std::thread t(std::move(task), 5);
    t.join();

    std::cout << result.get() << std::endl;
}
```

这个例子里最值得注意的是：

1. `packaged_task` 把 `work` 包起来了。
2. `get_future()` 把结果通道拿出来了。
3. 任务最后被一个线程真正执行。

这已经很接近线程池的工作方式了。

## 6. 这一节里最容易混的几个点

### 6.1 `std::thread` 和 `std::future` 不是一类东西

- `std::thread` 关注的是"有没有线程在执行"。
- `std::future` 关注的是"结果什么时候回来"。

这两个东西的职责不同，不要混成一个概念。

### 6.2 任务和结果最好分开理解

如果我把它们混在一起，代码很容易变成：

- 线程函数里到处写共享变量。
- 调用方只能靠打印或全局状态确认结果。

这样后面做线程池会很难扩展。

### 6.3 结果返回不是"附加功能"

线程池真正工程化的地方，不是"能起很多线程"，而是"能稳定地提交任务并拿回结果"。

这一节学的东西，实际上是给后面的任务队列和线程池接口铺路。

## 7. 本节练习主线

我在这一节希望最终能把下面这条链路想清楚：

1. 一个函数怎么被当成任务。
2. 一个任务怎么被包装起来。
3. 一个结果怎么被返回给调用者。
4. 这些东西怎么组合成线程池的任务提交模型。

## 8. 实践小 demo

这一节通过 6 个递进式的小示例，把前面讲的概念一个一个跑起来。

### Demo 1: Async future 基础

**需求**：用 `std::async` 提交一个计算任务，主线程用 `future.get()` 取结果。

**引入**：
- `std::async`：直接启动一个任务，自动返回 `future`。
- `std::launch::async`：强制异步执行（vs `deferred`）。
- `future.get()`：阻塞等待结果，如果结果已就绪则直接返回。

**实现**：

```cpp
#include <iostream>
#include <future>

int add(int a, int b) {
    return a + b;
}

int main() {
    std::future<int> result = std::async(std::launch::async, add, 5, 10);
    std::cout << "The result of 5 + 10 is: " << result.get() << std::endl;
    return 0;
}
```

**输出**：`The result of 5 + 10 is: 15`

### Demo 2: Packaged_task 单线程

**需求**：用 `std::packaged_task` 包装函数，获取 `future`，在子线程中执行并等待结果。

**引入**：
- `std::packaged_task<Sig>`：把一个可调用对象包装成可移动的任务。
- `get_future()`：从任务获取关联的 `future`。
- `std::move(task)`：转移任务所有权到线程。

**实现**：

```cpp
#include <iostream>
#include <future>
#include <thread>

int add(int a, int b) {
    return a + b;
}

int main() {
    std::packaged_task<int(int, int)> task(add);
    std::future<int> result = task.get_future();

    std::thread t(std::move(task), 5, 10);
    std::cout << "The result of 5 + 10 is: " << result.get() << std::endl;
    t.join();
    return 0;
}
```

**输出**：`The result of 5 + 10 is: 15`

**关键点**：`packaged_task` 把任务和结果通道绑在一起，这正是线程池的基石。

### Demo 3: Packaged task 队列

**需求**：实现最小任务队列，主线程提交任务，工作线程从队列取出并执行，提交者通过 `future` 等待结果。

**引入**：
- `std::queue<std::packaged_task<void()>>`：任务队列。
- `std::mutex` + `std::condition_variable`：同步队列访问。
- 多任务并发执行模式。

**实现**：

```cpp
#include <iostream>
#include <queue>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <future>
#include <functional>
#include <stdexcept>

class TaskQueue {
public:
    std::future<void> submit(std::function<void()> task) {
        std::packaged_task<void()> packagedTask(task);
        std::future<void> future = packagedTask.get_future();
        {
            std::lock_guard<std::mutex> lock(mtx);
            if (shutdown) {
                throw std::runtime_error("submit on stopped TaskQueue");
            }
            tasks.push(std::move(packagedTask));
        }
        cv.notify_one();
        return future;
    }

    void work() {
        while (true) {
            std::packaged_task<void()> task;
            {
                std::unique_lock<std::mutex> lock(mtx);
                cv.wait(lock, [this] { return !tasks.empty() || shutdown; });
                if (shutdown && tasks.empty()) {
                    return;
                }
                task = std::move(tasks.front());
                tasks.pop();
            }
            task();
        }
    }

    void stop() {
        {
            std::lock_guard<std::mutex> lock(mtx);
            shutdown = true;
        }
        cv.notify_all();
    }

private:
    std::queue<std::packaged_task<void()>> tasks;
    std::mutex mtx;
    std::condition_variable cv;
    bool shutdown = false;
};

int main() {
    TaskQueue taskqueue;
    std::thread worker(&TaskQueue::work, &taskqueue);

    auto future1 = taskqueue.submit([]() {
        std::this_thread::sleep_for(std::chrono::seconds(1));
        std::cout << "Task 1 completed" << std::endl;
    });

    auto future2 = taskqueue.submit([]() {
        std::this_thread::sleep_for(std::chrono::seconds(2));
        std::cout << "Task 2 completed" << std::endl;
    });

    auto future3 = taskqueue.submit([]() {
        std::this_thread::sleep_for(std::chrono::seconds(3));
        std::cout << "Task 3 completed" << std::endl;
    });

    future1.get();
    future2.get();
    future3.get();

    taskqueue.stop();
    worker.join();

    std::cout << "All tasks completed" << std::endl;
    return 0;
}
```

**输出**：
- `Task 1 completed`
- `Task 2 completed`
- `Task 3 completed`
- `All tasks completed`

**关键点**：
- `submit()` 里用 `packaged_task` 绑定任务和结果通道。
- `work()` 通过 `wait` 的谓词同时处理"有任务"与"关闭队列"。
- `stop()` 需要在锁保护下设置 `shutdown`，避免并发读写风险。

### Demo 4: Promise future

**需求**：用 `std::promise` 在工作线程中设置值，主线程通过 `future` 获取。

**引入**：
- `std::promise<T>`：在线程中设置值。
- `promise.set_value()`：设置结果。
- `promise.get_future()`：获取关联的 `future`。

**实现**：

```cpp
#include <iostream>
#include <thread>
#include <future>
#include <chrono>

int main() {
    std::promise<int> prom;
    std::future<int> result = prom.get_future();

    std::thread worker([&prom]() {
        std::this_thread::sleep_for(std::chrono::seconds(2));
        std::cout << "\nWorker thread has set the result." << std::endl;
        prom.set_value(42);
    });

    std::cout << "Waiting for the result..." << std::endl;
    int res = result.get();
    std::cout << "Result: " << res << std::endl;
    worker.join();
    return 0;
}
```

**输出**：

```
Waiting for the result...
（2秒后）
Worker thread has set the result.
Result: 42
```

**关键点**：

- `promise` 不绑定任何函数，结果由你自己在任意地方调用 `set_value()` 写入。这和 `packaged_task` 的核心区别在于：`packaged_task` 的结果来自函数的返回值，`promise` 的结果来自你手动触发的那一刻。
- `get_future()` 只能调一次，重复调用会抛 `std::future_error`。先拿到 future，再把 promise 传给线程。
- 这里用 `[&prom]` 捕获引用，worker 线程里操作的就是 main 里那个真实的 promise 对象。使用引用捕获时要确保 promise 的生命周期覆盖线程的整个运行周期。
- `promise` 适合的典型场景：结果不来自函数返回，而来自外部事件、回调、硬件信号等你自己决定"现在写结果"的时机。

### Demo 5: Future 超时

**需求**：提交一个长时间运行的任务，主线程用 `wait_for` 判断超时并采取备用策略。

**引入**：
- `future.wait_for(timeout)`：等待有限时间，返回 `future_status`。
- `future_status::ready / timeout / deferred`：三种状态。

**实现**：

```cpp
#include <iostream>
#include <future>
#include <chrono>

int slowTask() {
    std::this_thread::sleep_for(std::chrono::seconds(2));
    return 42;
}

int main() {
    std::future<int> result = std::async(std::launch::async, slowTask);

    auto status = result.wait_for(std::chrono::seconds(3));
    if (status == std::future_status::ready) {
        std::cout << "Result: " << result.get() << std::endl;
    } else {
        std::cout << "Task timeout, using fallback value" << std::endl;
    }
    return 0;
}
```

**两种路径对比**：

把 `wait_for` 的参数改成 `std::chrono::milliseconds(500)`，任务还没跑完就超时，走 else 分支：

```
Task timeout, using fallback value
```

等待时间足够长时（如上面的 3 秒），结果正常返回：

```
Result: 42
```

**关键点**：

- `wait_for()` 不取消任务，只是"我不等了"。超时后后台任务依然在跑，直到完成。
- `future_status` 有三种：`ready`（结果就绪）、`timeout`（超时）、`deferred`（任务还没开始，用了 `launch::deferred`）。如果不用 `launch::async` 而用 `launch::deferred`，`wait_for` 会立即返回 `deferred`，什么都不等。
- `wait_for()` 可以多次调用，每次重新等一段时间，直到你决定放弃。

### Demo 6: Future 异常处理

**需求**：让任务抛出异常，演示 `future.get()` 如何将异常传播给调用方，并在主线程中捕获它。

**引入**：
- 任务内抛出异常时，异常被捕获并存储在 `future` 的共享状态里。
- `future.get()` 调用时如果共享状态里是异常，会重新抛出，而不是返回值。
- 这使得异常能跨线程传播，调用方用普通的 `try/catch` 就能处理。

**实现**：

```cpp
#include <iostream>
#include <future>
#include <stdexcept>

int risky_task() {
    throw std::runtime_error("Task failed!");
    return 0;
}

int main() {
    std::future<int> result = std::async(std::launch::async, risky_task);

    try {
        int value = result.get();
        std::cout << "Result: " << value << std::endl;
    } catch (const std::exception& e) {
        std::cout << "Caught exception: " << e.what() << std::endl;
    }
    return 0;
}
```

**输出**：`Caught exception: Task failed!`

**关键点**：

- 任务线程里抛出的异常不会直接崩到主线程，而是被运行时捕获、转成 `std::exception_ptr`，存进 `future` 的共享状态。`get()` 取值时检测到是异常，就调 `std::rethrow_exception()` 重新抛出来。
- 这个机制对 `std::async`、`std::packaged_task` 都自动成立。用 `std::promise` 时则需要手动调 `promise.set_exception(std::current_exception())` 才能把异常送进去。
- 线程池里这个机制很有价值：提交者不需要关心任务在哪个线程里跑，只需要在 `get()` 外套一层 `try/catch`，就能统一处理失败情况，不用在每个线程函数里单独做错误传递。

## 9. 小结

到这里，线程学习就从"线程能运行"推进到了"任务能返回结果"。

这一步很关键，因为线程池不是单纯的线程集合，而是一个"任务调度 + 结果回收"的系统。
