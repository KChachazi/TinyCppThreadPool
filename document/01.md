# 线程生命周期：从创建到收尾

程序默认是单线程的——所有代码跑在同一条执行路径上，一件事做完再做下一件。多线程改变了这一点：你可以同时启动多条执行路径，让它们并发地推进各自的任务。这在很多场景下很有用，比如一个线程在等网络响应，另一个线程继续处理用户输入，两者互不阻塞。

但多线程编程引入了一类新的问题：线程是有生命周期的，它什么时候启动、什么时候结束、结束之后谁来收尾——这些都需要程序员显式管理。如果管理得不到位，轻则结果错误，重则进程崩溃。很多人写第一个多线程程序时就在这里踩了坑，程序莫名其妙地调 `std::terminate()` 退出，没有任何有用的报错信息。

这篇文章从 `std::thread` 的基本用法出发，把线程生命周期管理的核心规则讲清楚。主要包含这几部分：`std::thread` 是什么、它暴露了哪些接口；线程对象和底层线程的关系，以及这个关系为什么会导致程序崩溃；`joinable()`、`join()`、`detach()` 分别是什么意思、该怎么选；并发和并行的区别，以及这个区别能解释哪些常见疑惑；最后是一个完整可运行的例子，和关于主线程退出时序的一个重要注意事项。

## 1. std::thread

C++11 之前，创建线程要直接调用平台 API——Windows 上是 `CreateThread`，Linux 上是 `pthread_create`。而在 C++11 之后，`std::thread` 把这些平台差异包进一个统一的类，我们就可以在标准 C++ 里直接启动线程，不用关心底层系统调用。

创建线程就是构造一个 `std::thread` 对象，把要执行的函数和它的参数一起传进去，线程立刻启动，不需要额外的 `start()` 调用：

```cpp
std::thread t(Func, arg1, arg2, ...);
```

传进去的可以是普通函数、lambda、仿函数，或者绑定了对象的成员函数，例如：

```cpp
std::thread t1(free_function, 42);
std::thread t2([](int x) { /* ... */ }, 42);
std::thread t3(&MyClass::method, &obj, 42);
```

`std::thread` 本身暴露的接口并不多，主要用到的有：

| 成员函数 | 作用 |
|----------|------|
| `join()` | 等待线程结束，回收管理关系 |
| `detach()` | 放手，线程独立运行 |
| `joinable()` | 查询线程对象是否关联着一个活跃的底层线程 |
| `get_id()` | 返回线程 ID |
| `hardware_concurrency()` | 静态函数，返回硬件支持的并发线程数（通常等于核心数） |

需要注意，`joinable()` 为真的对象被析构时，程序直接崩。

## 2. 线程对象是管理句柄，不是线程本身

`std::thread` 管理的是一个底层操作系统线程，但它自己不是那个线程。真正执行代码的是操作系统调度的底层线程。`std::thread` 对象只是 C++ 层面用来管理它的包装，我们可以通过它 `join()`、`detach()`、查状态。这里可以类比 `std::unique_ptr`——指针对象不是堆内存本身，它只是管理者。如果管理者在被管对象的生命期结束前消失，就会出现严重的问题。

对于 `std::thread` 而言，如果线程对象被析构时，底层线程还没有被 join 或 detach，C++ 运行时无法知道"这个线程最终应该怎么处理"，于是选择了最激进的策略——调用 `std::terminate()`，导致整个进程挂掉。

> 每一个 `joinable()` 为真的 `std::thread` 对象，在析构前必须被 `join()` 或 `detach()` 处理。这是硬性要求，不是建议。

## 3. joinable()

前面提到，每个真的 `std::thread` 对象都必须在析构前处理，那首先有一个问题是，我们如何知道这个线程需要被处理。`joinable()`就是为了解决这个问题的。

一个线程可以 `joinable()` 的含义是：这个线程对象当前对应着一个活跃的底层线程，还没有被处理过。

不再 `joinable` 的线程对象主要有：默认构造的线程对象（从未关联过底层线程）、已经 `join()` 过的、已经 `detach()` 过的。

`joinable()` 检查是个防御性习惯，任何要调 `join()` 或 `detach()` 的地方先查一下，避免对无效对象操作：

```cpp
if (t.joinable()) {
    t.join();
}
```

## 4. join()/detach()

处理一个 `joinable` 线程只有两种选择：

| 操作 | 语义 | 调用方行为 | 线程对象状态 |
|------|------|-----------|------------|
| `join()` | 等它跑完，回收管理关系 | 阻塞直到线程结束 | 变为 not joinable |
| `detach()` | 放手，线程独立运行 | 立即返回，失去控制权 | 变为 not joinable |

`detach()` 之后没有任何人能再等这个线程、检查它的状态或者和它交互——底层线程会一直跑到函数返回为止，但调用方对此一无所知。入门阶段优先用 `join()`，等把资源管理理顺之后再考虑 `detach()`。

## 5. 并发不等于并行

并发和并行经常被混用，但它们描述的是两件不同的事：

- **并发（Concurrency）**：同一时间段内处理多个任务，不要求同时执行，靠快速切换就能实现，单核 CPU 就够。
- **并行（Parallelism）**：同一时刻真正同时执行，需要多个处理单元，多核 CPU 或多台机器。

单核机器上跑两个线程，操作系统会把 CPU 时间切成很小的片（time slice，通常几毫秒），轮流分给每个线程。切换时保存当前线程的寄存器和栈指针，恢复下一个线程的，这个过程叫**上下文切换**（context switch）。切换足够快，人感觉不到停顿，看起来像同时在跑——但物理上某一时刻只有一个线程在跑。这些知识是操作系统的内容，具体可以查询 **时间片轮转(RR)**，‌比如 Windows 采用基于优先级的抢占式调度算法，结合多级反馈队列和时间片轮转机制。‌‌‌‌

此外还有一个常见误解：多线程不一定比单线程快。如果任务本身是纯 CPU 密集型的，在单核机器上加线程只是多了上下文切换的开销，反而更慢。多线程真正划算的场景，是任务里有大量 I/O 等待，或者机器有多核可以真正并行计算。

## 6. 简单示例

```cpp
#include <iostream>
#include <thread>
#include <chrono>

void worker(int id) {
    std::this_thread::sleep_for(std::chrono::milliseconds(50));
    std::cout << "worker " << id
              << "  tid=" << std::this_thread::get_id() << "\n";
}

int main() {
    std::cout << "main  tid=" << std::this_thread::get_id() << "\n";

    std::thread t1(worker, 1);
    std::thread t2(worker, 2);

    // t1、t2 在这里是 joinable 的，必须处理，否则析构时 terminate
    if (t1.joinable()) t1.join();
    if (t2.joinable()) t2.join();

    std::cout << "all done\n";
    return 0;
}
```
输出的线程 ID 和 worker 的打印顺序每次都可能不同——这正是并发调度的正常现象。关键在于两个线程对象都在析构前被 `join()` 了，程序能干净退出。

## 7. 主线程不能过早退出

如果 `main()` 先返回，整个进程退出，还没跑完的子线程会被一起终止——不管它们在做什么，不管有没有 `detach()`。

实践里，主线程的结束点必须在所有子线程完成之后。用 `join()` 显式等待是最直接的保证方式。这也是线程池的析构函数里总要 `join()` 所有 worker 的根本原因——对象销毁时不能留下还在访问它的线程。
